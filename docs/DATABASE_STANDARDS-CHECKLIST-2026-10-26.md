# PostgreSQL schema review checklist (Next.js + Prisma 6 + Neon)

Compiled 2026-10-26. Each criterion reads "a good schema does X; *check* by Y" and cites its source and the source's year or version.
Version baseline: PostgreSQL 18 is the current stable major. PG 19 is at RC 1, with GA planned for 19 Nov 2026 ([postgresql.org news, 2026](https://www.postgresql.org/about/news/postgresql-19-rc-1-released-3409/)). In Feb 2026 Neon's supported minors were 17.8 and 18.2 ([Neon changelog 2026-02-27](https://neon.com/docs/changelog/2026-02-27)). Doc links point to `/docs/18/` unless noted. Run `SELECT version();` before applying anything that depends on the version.

Legend: **[PG]** PostgreSQL docs · **[PR]** Prisma docs · **[NE]** Neon docs.

## Context-specific findings (read first)

- **Neon Free storage is 1 GB per project (20 GB across all projects). 100 CU-hours per project per month. Scale to zero after 5 min, and it can't be disabled. Max 2 CU. 5 GB egress. 6-hour restore history.** Once storage hits the cap, inserts, updates and deletes fail. Once CU-hours or egress run out, compute is suspended. Data is not deleted. ([NE plans, accessed 2026-10](https://neon.com/docs/introduction/plans); [NE FAQ, 2026](https://neon.com/faqs/free-plan-limits-and-quotas)). Some search snippets still quote an older 0.5 GB figure. The plans page and the FAQ both say 1 GB.
- **pg_stat_statements / Query history resets whenever the Neon compute suspends or restarts, including scale-to-zero.** Snapshot it before you rely on it ([NE monitor query performance, 2026](https://neon.com/docs/introduction/monitor-query-performance)).
- **Prisma `DateTime` maps to `timestamp(3)` (without time zone) by default.** You must ask for `@db.Timestamptz(3)` explicitly ([PR type system](https://www.prisma.io/docs/orm/prisma-client/type-safety/prisma-type-system)). Precision 0 rounds ([PR Optimize recommendation](https://www.prisma.io/docs/v6/postgres/query-optimization/recommendations/avoid-timestamp-timestampz-0)).
- **Prisma 6 default referential actions:** for an optional relation, `onDelete: SetNull` and `onUpdate: Cascade`. For a required relation, `onDelete: Restrict` and `onUpdate: Cascade` ([PR v6 referential actions](https://www.prisma.io/docs/orm/v6/prisma-schema/data-model/relations/referential-actions)).
- **Partial indexes reached Prisma schema only in v7.4 (Feb 2026), behind the `partialIndexes` preview flag** ([PR changelog 2026-02-11](https://www.prisma.io/changelog/2026-02-11)). Prisma 6 can't express them, or CHECK constraints, triggers or views, in the schema. Add them as hand-edited SQL via `migrate dev --create-only` ([PR v6 unsupported features](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/unsupported-database-features)).

## 1. Normalization, denormalization and keys

- [ ] **1.1 3NF by default; denormalize only on measured need.** Each fact (a speaker's score in a round, a motion's text, a tournament's date) is stored once. Copies exist only behind a documented refresh path. *Check:* for every repeated column such as `tournament_name` on a results table, find the EXPLAIN ANALYZE evidence or the refresh mechanism. Src: [archman.dev normalization vs denormalization, 2025](https://archman.dev/docs/data-architecture-and-persistence/data-modeling-and-access/normalization-vs-denormalization); [dbschema "When not to normalise", 2025](https://dbschema.com/blog/design/when-not-to-normalise/).
- [ ] **1.2 Read-heavy per-person analytics use materialized views (or summary tables), not duplicated columns.** If refreshed `CONCURRENTLY`, the view needs a unique, non-partial, column-only index. Without `CONCURRENTLY`, a refresh can block readers. *Check:* `\d+ mv_name` shows a unique index, and the refresh job uses `CONCURRENTLY`. Src: [PG 18 REFRESH MATERIALIZED VIEW](https://www.postgresql.org/docs/18/sql-refreshmaterializedview.html).
- [ ] **1.3 Surrogate PK plus a UNIQUE constraint on the natural key.** Scraped entities (tournament = source + external id/slug; round = tournament + round number; ballot row = round + team/speaker) carry a declared natural-key UNIQUE, which is also what makes upserts work (6.1). *Check:* every table with a surrogate `id` has at least one other UNIQUE or the reason is documented. Src: [PG 18 INSERT ON CONFLICT (arbiter must be unique index/constraint)](https://www.postgresql.org/docs/18/sql-insert.html).
- [ ] **1.4 Composite keys are used for pure join/link tables** (motion_tag, judge_assignment), not a meaningless extra id. *Check:* link tables have PK `(a_id, b_id)` or a UNIQUE on it. Src: [PG 18 constraints (multi-column PK example)](https://www.postgresql.org/docs/18/ddl-constraints.html).
- [ ] **1.5 Key type is chosen deliberately.** Use `bigint` identity for internal tables. Use UUIDv7 (native `uuidv7()` in PG 18) only where an id is exposed publicly or generated client-side. Avoid random UUIDv4 PKs on large, write-heavy tables: they cause B-tree page splits and index fragmentation, and they are 16 bytes against 8. *Check:* list PK types (`SELECT table_name, data_type FROM information_schema.columns WHERE column_name='id'`), and flag `text` cuid/uuid PKs on high-row-count tables. Src: [credativ "UUIDv4 vs UUIDv7 in PG18", Dec 2025](https://www.credativ.de/en/blog/postgresql-en/a-deeper-look-at-old-uuidv4-vs-new-uuidv7-in-postgresql-18/); [DbVisualizer UUIDv7 in PG18, 2025](https://www.dbvis.com/thetable/uuidv7-in-postgresql-18-what-you-need-to-know/); [AppMaster UUID vs bigint, Sep 2025](https://appmaster.io/blog/uuid-vs-bigint-postgresql-ids).
- [ ] **1.6 Identity, not serial.** Hand-written SQL uses `GENERATED ALWAYS|BY DEFAULT AS IDENTITY`, not `serial`. Prisma `@default(autoincrement())` emits `serial`, so record that as a known deviation. *Check:* `SELECT table_name, column_name FROM information_schema.columns WHERE column_default LIKE 'nextval%'`. Src: [PG wiki Don't Do This, ed. 2024](https://wiki.postgresql.org/wiki/Don't_Do_This); [PG 18 CREATE TABLE identity](https://www.postgresql.org/docs/18/sql-createtable.html).
- [ ] **1.7 Gaps in identity/sequence values are accepted, not "fixed".** *Check:* no code depends on contiguous ids, for example by deriving a rank from `id`. Src: [PG 18 numeric types / serial note](https://www.postgresql.org/docs/18/datatype-numeric.html).

## 2. Constraints as the integrity layer

- [ ] **2.1 Every relationship is a declared FOREIGN KEY with a deliberate ON DELETE action.** Use `CASCADE` for owned children (round results under a tournament, parser-run rows under a source document), `RESTRICT`/`NO ACTION` for shared references (person, institution), and `SET NULL` only for optional links. `SET NULL (col)` column lists exist for composite FKs. *Check:* `SELECT conrelid::regclass, conname, confdeltype FROM pg_constraint WHERE contype='f'`. Compare with intent, and remember Prisma's defaults (see the context findings). Src: [PG 18 constraints](https://www.postgresql.org/docs/18/ddl-constraints.html); [PR v6 referential actions](https://www.prisma.io/docs/orm/v6/prisma-schema/data-model/relations/referential-actions).
- [ ] **2.2 NOT NULL wherever a value is always required.** That includes FK columns of mandatory relations, `created_at`, score columns on completed ballots, and job status. *Check:* review `is_nullable='YES'` columns in `information_schema.columns` one by one. Src: [PG 18 constraints](https://www.postgresql.org/docs/18/ddl-constraints.html).
- [ ] **2.3 CHECK constraints encode domain rules.** Examples: speaker score within the format's legal range, `round_number > 0`, `ended_at >= started_at`, `attempts >= 0`, `status IN (...)`. In Prisma 6 these live in hand-edited migration SQL. *Check:* `SELECT conrelid::regclass, pg_get_constraintdef(oid) FROM pg_constraint WHERE contype='c'`. Src: [PG 18 constraints](https://www.postgresql.org/docs/18/ddl-constraints.html); [PR v6 unsupported features workflow](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/unsupported-database-features).
- [ ] **2.4 UNIQUE with nullable columns uses `NULLS NOT DISTINCT` (PG 15+) when "one NULL" is meant to be unique.** One example is `(tournament_id, speaker_id, round_id)` where `round_id` is NULL for totals. The default allows many NULL duplicates. *Check:* for every unique index with a nullable column, `pg_get_indexdef` shows the intended NULLS clause. Src: [PG 18 constraints](https://www.postgresql.org/docs/18/ddl-constraints.html); [dbi-services PG15 NULLS NOT DISTINCT, 2022](https://www.dbi-services.com/blog/postgresql-15-new-option-for-null-handling-in-unique-constraints/).
- [ ] **2.5 Exclusion or temporal constraints where overlap is the rule.** One case is a validity range per entity (SCD history, see 6.6). PG 18 adds `PRIMARY KEY/UNIQUE (... , valid_at WITHOUT OVERLAPS)` and `FOREIGN KEY (..., PERIOD ...)`, which need `btree_gist` for scalar columns. *Check:* any `*_valid_from/_valid_to` pair has an EXCLUDE or WITHOUT OVERLAPS constraint. Src: [PG 18 CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html).
- [ ] **2.6 Constraints on big existing tables are added `NOT VALID` and then `VALIDATE CONSTRAINT`.** Validation takes only SHARE UPDATE EXCLUSIVE. PG 18 also has `NOT ENFORCED` for informational CHECKs. *Check:* no `convalidated = false` left behind by accident: `SELECT conname FROM pg_constraint WHERE NOT convalidated`. Src: [PG 18 ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html).

## 3. Data types

- [ ] **3.1 Scores use `numeric(p,s)` (or integer half-points), not `real`/`double precision`.** Floats are inexact, and the docs advise `numeric` where exact storage and calculation are needed. Debate scores such as 75.5 and averages must sum and compare exactly. *Check:* `SELECT table_name, column_name, data_type FROM information_schema.columns WHERE data_type IN ('real','double precision')`. Src: [PG 18 numeric types](https://www.postgresql.org/docs/18/datatype-numeric.html).
- [ ] **3.2 All points in time are `timestamptz`.** Plain `timestamp` lacks zone context, even for UTC values. Never use precision 0, which rounds into the future. Tournament *dates* with no time component use `date`. *Check:* `data_type = 'timestamp without time zone'` should return no rows, and every Prisma `DateTime` carries `@db.Timestamptz(3)`. Src: [PG wiki Don't Do This, ed. 2024](https://wiki.postgresql.org/wiki/Don't_Do_This); [PR type system](https://www.prisma.io/docs/orm/prisma-client/type-safety/prisma-type-system).
- [ ] **3.3 `text` by default; no arbitrary `varchar(n)`/`char(n)`.** Enforce real limits with `CHECK (length(x) <= n)` or a format regex. *Check:* grep migrations for `VARCHAR(`/`CHAR(`. Src: [PG wiki Don't Do This, ed. 2024](https://wiki.postgresql.org/wiki/Don't_Do_This).
- [ ] **3.4 Enums only for small, stable, closed sets** (job status, side = gov/opp). Enum values can be added or renamed but never removed, and the sort order is fixed. For evolving sets with metadata (formats, motion tags, regions), use a lookup table + FK or a CHECK list. *Check:* every `CREATE TYPE ... AS ENUM` is reviewed against "will a value ever be retired?". Src: [PG 18 enum types](https://www.postgresql.org/docs/18/datatype-enum.html).
- [ ] **3.5 `jsonb` (not `json`) only for genuinely schemaless or atomic payloads**: raw parser output, source metadata. Keep the structure fairly fixed and the documents a manageable size. Any update locks the whole row. Anything queried or joined on (scores, person ids, tags) is a real column or table. *Check:* list jsonb columns and the queries that filter inside them, then promote hot keys to columns. Src: [PG 18 JSON types](https://www.postgresql.org/docs/18/datatype-json.html).
- [ ] **3.6 Arrays only for small, ordered, owned value lists with no FK need.** Community motion tags with counts or moderation belong in a link table (1.4), not `text[]`. *Check:* no array column holds ids of other rows. Src: [PG 18 constraints (FKs cannot target array elements; use link tables)](https://www.postgresql.org/docs/18/ddl-constraints.html). (Note: no single official "arrays vs link table" guideline was found. This item is an inference from FK semantics.)
- [ ] **3.7 No `money`, `timetz`, `char(n)`, or `SQL_ASCII` encoding.** *Check:* type scan plus `SHOW server_encoding` = UTF8. Src: [PG wiki Don't Do This, ed. 2024](https://wiki.postgresql.org/wiki/Don't_Do_This).

## 4. Indexing

- [ ] **4.1 Every FK column (or the leading column of a composite) is indexed.** PG does not index referencing columns automatically, and parent deletes and cascades scan the child table without that index. *Check:* run a query joining `pg_constraint (contype='f')` to `pg_index` on leading `indkey`, and list any FK without a matching index. Src: [PG 18 constraints](https://www.postgresql.org/docs/18/ddl-constraints.html); [Percona PMM unused-index advisor (FK caveat), 2025](https://pmm-doc-3.onrender.com/advisors/checks/postgresql-unused-index-check.html).
- [ ] **4.2 B-tree composite order matches the query.** Equality columns lead, then at most one range column. Example: per-person history uses `(speaker_id, tournament_date)` or `(person_id, round_id)`. Indexes wider than 3 columns are rarely useful. PG 18 skip scan helps only when the leading column has few distinct values. *Check:* compare each composite index with the top `pg_stat_statements` WHERE/ORDER BY clauses. Src: [PG 18 multicolumn indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html).
- [ ] **4.3 Partial indexes for skewed predicates.** Examples: the job queue `WHERE status='pending'`, `WHERE deleted_at IS NULL`, and unique-when-active rules. In Prisma 6 they go in custom migration SQL (v7.4+ preview supports `where:`). *Check:* the queue poll query's EXPLAIN uses a small partial index. Src: [PR v6 unsupported features (partial unique index example)](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/unsupported-database-features); [PR changelog 2026-02-11](https://www.prisma.io/changelog/2026-02-11).
- [ ] **4.4 Covering `INCLUDE` indexes only for hot, mostly static read paths.** Index-only scans pay off only when pages are all-visible, and payload columns bloat the index. *Check:* EXPLAIN shows `Index Only Scan` with low `Heap Fetches`. Src: [PG 18 index-only scans](https://www.postgresql.org/docs/18/indexes-index-only-scans.html).
- [ ] **4.5 GIN only where jsonb/array containment is actually queried.** Prefer `jsonb_path_ops` (smaller and faster for `@>`) or a targeted expression GIN index on the sub-key over whole-document `jsonb_ops`. *Check:* every GIN index has a matching `@>`/`?` query in pg_stat_statements. Src: [PG 18 JSON types §8.14.4](https://www.postgresql.org/docs/18/datatype-json.html).
- [ ] **4.6 BRIN only for very large, append-only tables whose column correlates with physical order** (e.g. `fetched_at` on snapshots or parser-run logs). It is not useful at roughly 1,000-tournament scale. *Check:* `SELECT correlation FROM pg_stats WHERE ...` is close to ±1 before choosing BRIN. Src: [PG 18 BRIN](https://www.postgresql.org/docs/18/brin.html).
- [ ] **4.7 Unused and duplicate indexes are found and removed, with care.** Flag rows where `pg_stat_user_indexes.idx_scan = 0` across a long stats window. Exclude PK/unique/constraint-backing indexes and FK-supporting ones. On Neon, stats reset on compute restart, so sample over time. *Check:* run the postgres.ai query and compare against `pg_stat_database.stats_reset`. Src: [postgres.ai how to find unused indexes, 2025](https://postgres.ai/docs/postgres-howtos/performance-optimization/indexing/how-to-find-unused-indexes); [PG 18 monitoring stats](https://www.postgresql.org/docs/18/monitoring-stats.html).
- [ ] **4.8 Indexes on live tables are built `CONCURRENTLY`.** This can't run inside a transaction block, and a failure leaves an INVALID index to drop. *Check:* `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid` returns nothing. Confirm that the migration file containing CONCURRENTLY is not wrapped in a transaction by the runner. Src: [PG 18 CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html).

## 5. Large blobs, raw snapshots and retention

- [ ] **5.1 The blob placement decision is explicit.** `bytea` gives ACID and single backup but has a 1 GB per value cap, costs memory, and slows backups. Object storage (S3/R2/Neon Object Storage) with a key, hash and size in Postgres is the pattern Neon's own guide recommends for files. On a 1 GB Free cap, gzipped HTML in `bytea` is the most likely storage consumer. *Check:* `SELECT pg_size_pretty(pg_total_relation_size('raw_snapshot'))` as a share of `pg_database_size(current_database())`. Src: [PG wiki BinaryFilesInDB, ed. 2021](https://wiki.postgresql.org/wiki/BinaryFilesInDB); [NE file storage guide, 2026](https://neon.com/docs/guides/file-storage); [NE plans](https://neon.com/docs/introduction/plans).
- [ ] **5.2 Already-compressed `bytea` avoids pointless re-compression.** Use `ALTER TABLE ... ALTER COLUMN body SET STORAGE EXTERNAL` (out-of-line, no compression). Values over ~2 kB are TOASTed. *Check:* `\d+ raw_snapshot` shows storage `external` for the gzip column. Src: [PG 18 TOAST](https://www.postgresql.org/docs/18/storage-toast.html).
- [ ] **5.3 Blob tables are kept narrow and out of hot queries.** The blob sits in its own table (1:1 with source_document), so analytics never `SELECT *` it and Prisma never loads it implicitly. *Check:* no Prisma `findMany` on the parent model includes the blob relation by default. Src: [PG 18 TOAST (out-of-line storage only read when the column is referenced)](https://www.postgresql.org/docs/18/storage-toast.html).
- [ ] **5.4 Snapshots carry a content hash and dedupe on it.** Store `sha256(body)` with a UNIQUE `(source_url, content_sha256)` so an unchanged re-fetch stores nothing new. *Check:* duplicate-hash count = 0. Src: [PG 18 binary string functions (`sha256(bytea)`)](https://www.postgresql.org/docs/18/functions-binarystring.html).
- [ ] **5.5 Raw data has a written retention rule and a scheduled purge.** Example: keep the latest N snapshots per source plus any snapshot referenced by a parser run. After bulk deletes, plain VACUUM makes space reusable but does not shrink files. Only `VACUUM FULL` (ACCESS EXCLUSIVE, needs ~table-size free space) returns it. *Check:* a purge job exists and is logged, and you can track snapshot table size over time. Src: [PG 18 routine vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html); [GDPR Art. 5(1)(e) storage limitation commentary, 2025](https://www.legiscope.com/blog/gdpr-article-5-storage-limitation-eur-lex.html).

## 6. Provenance, lineage and idempotent ingestion

- [ ] **6.1 Every ingest write is an idempotent upsert on a natural key.** Use `INSERT ... ON CONFLICT (natural key) DO UPDATE SET ... WHERE <changed>` or `DO NOTHING`. Prisma `upsert` needs a `@@unique` on the same columns. The batch must not contain the same key twice (cardinality violation). *Check:* re-run one tournament's ingest twice and confirm row counts and `updated_at` are unchanged the second time. Src: [PG 18 INSERT ON CONFLICT](https://www.postgresql.org/docs/18/sql-insert.html).
- [ ] **6.2 Provenance follows an entity / activity / agent model.** Source document = entity, parser run = activity with parser version, started/finished, status and error, scraper/user = agent. Each derived fact row has `source_document_id` and/or `parser_run_id` (wasGeneratedBy / wasDerivedFrom). *Check:* pick 5 random score rows and trace each to its HTML snapshot and parser version. Src: [W3C PROV overview (PROV-DM 2013 Rec.)](https://en.wikipedia.org/wiki/W3C_Prov); [prov Python docs, PROV-DM](https://prov.readthedocs.io/en/latest/explanation/prov-dm.html).
- [ ] **6.3 Run records have a start and a terminal state** (COMPLETE / FAIL / ABORT), so orphaned "running" runs can be detected. This is aligned with the OpenLineage run model. *Check:* `SELECT count(*) FROM parser_run WHERE status='running' AND started_at < now()-interval '1 hour'`. Src: [OpenLineage facets/spec, 2025-26](https://openlineage.io/docs/guides/facets).
- [ ] **6.4 The job queue uses `FOR UPDATE SKIP LOCKED` only for claiming,** with a partial index on pending rows, an `attempts` counter, a `locked_until`/visibility timeout, and a dead-letter state. The docs warn that SKIP LOCKED gives an inconsistent view, so it is not for general reads. *Check:* the claim query is `... WHERE status='pending' ORDER BY ... LIMIT n FOR UPDATE SKIP LOCKED`, and no reporting query uses SKIP LOCKED. Src: [PG 18 SELECT locking clause](https://www.postgresql.org/docs/18/sql-select.html).
- [ ] **6.5 Re-parsing is reproducible.** Derived tables can be rebuilt from stored snapshots plus the parser version, and old and new outputs are distinguishable by `parser_run_id`. *Check:* a documented "reparse tournament X" path exists that doesn't refetch. Src: [OpenLineage facets (run/job/dataset)](https://openlineage.io/docs/guides/facets).
- [ ] **6.6 Corrections to published results keep history.** For SCD Type 2 or bitemporal changes, use `valid_from/valid_to` (or a `tstzrange`) with a non-overlap constraint, instead of silently overwriting when a tab is corrected. *Check:* the 2.5 constraint exists on any history table. Src: [PG 18 CREATE TABLE WITHOUT OVERLAPS / PERIOD](https://www.postgresql.org/docs/18/sql-createtable.html).
- [ ] **6.7 Upserts report what changed.** PG 18 `RETURNING WITH (OLD AS o, NEW AS n)` lets the ingest log diffs per row. *Check:* the ingest logs inserted/updated/unchanged counts per run. Src: [PG 18 INSERT](https://www.postgresql.org/docs/18/sql-insert.html).

## 7. Schema migrations discipline

- [ ] **7.1 Use expand → migrate data → contract for any rename, type change or split.** Add the new column, dual-write, backfill in a separate step, switch reads, then drop the old column in a later release. *Check:* no single migration both drops and adds the "same" column. Src: [PR expand-and-contract guide, 2026](https://www.prisma.io/docs/guides/database/data-migration); [PR v6 customizing migrations](https://www.prisma.io/docs/v6/orm/prisma-migrate/workflows/customizing-migrations).
- [ ] **7.2 `migrate deploy` runs only from CI in production; `migrate dev` never touches prod.** `migrate dev` may prompt a reset on drift and uses a shadow DB. *Check:* the CI script calls `prisma migrate deploy`, and no `db push` runs against prod. Src: [PR v6 development and production](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/development-and-production).
- [ ] **7.3 Migrations use the direct (non-pooled) Neon URL** (`directUrl`, or the `prisma.config.ts` datasource). The app uses the `-pooler` URL. *Check:* the env split exists, and migrations succeed without "prepared statement already exists" errors. Src: [Neon blog: Prisma DX improvements, 2024](https://neon.com/blog/prisma-dx-improvements).
- [ ] **7.4 Lock-safe DDL.** Set `lock_timeout` (and `statement_timeout`) at the top of risky migrations. Use `CREATE INDEX CONCURRENTLY`, `ADD CONSTRAINT ... NOT VALID` + `VALIDATE`, and `SET NOT NULL` after a validated `CHECK (col IS NOT NULL)` (the scan is skipped). `ADD COLUMN ... DEFAULT <non-volatile>` needs no rewrite, but a volatile default does. *Check:* lint migrations with Squawk (`require-concurrent-index-creation`, `require-lock-timeout`). Src: [PG 18 ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html); [squawk-cli on PyPI, 2026](https://pypi.org/project/squawk-cli/).
- [ ] **7.5 Backfills run in batches outside the DDL migration** (a script or job keyed by PK range, resumable, idempotent), not as one giant `UPDATE` inside `migration.sql`. *Check:* no `UPDATE` without a `WHERE` key range in migration files touching large tables. Src: [PR expand-and-contract guide, 2026](https://www.prisma.io/docs/guides/database/data-migration).
- [ ] **7.6 Hand-written SQL (CHECKs, partial indexes, triggers, extensions) lives in committed migration files, not applied manually.** Extensions are created inside migrations so the shadow DB has them too. *Check:* `prisma migrate diff` shows no unexplained drift, and every `pg_constraint` CHECK appears in some migration file. Src: [PR v6 unsupported features](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/unsupported-database-features).
- [ ] **7.7 Test risky migrations on a Neon branch first** (copy-on-write clone of prod; Free = 10 branches/project). *Check:* the PR notes the branch name and the migration timing. Src: [NE plans](https://neon.com/docs/introduction/plans).

## 8. Data quality checks and monitoring

- [ ] **8.1 Push invariants into constraints first (sections 2-3); test the rest with SQL assertions that return violating rows.** This mirrors dbt's `unique`, `not_null`, `accepted_values` and `relationships` tests, where zero rows means pass. *Check:* a `dq/*.sql` suite runs after each ingest and fails the run when rows are returned. Src: [dbt data tests docs, 2026](https://docs.getdbt.com/docs/build/data-tests); [dbt available tests FAQ](https://docs.getdbt.com/faqs/Tests/available-tests).
- [ ] **8.2 Domain reconciliation checks run per tournament.** Examples: team total equals the sum of speaker scores; every round has the expected number of ballots; elimination brackets halve correctly; no speaker appears twice in one round. *Check:* violations are stored per `parser_run_id` with a severity.
- [ ] **8.3 Freshness and volume monitoring.** Track `max(fetched_at)` per source, job-queue depth and age of the oldest pending job, and rows inserted per run compared with the trailing median. *Check:* a dashboard or alert exists for "no successful ingest in N days" and "pending job older than X". Src: [dbt data quality checks (freshness), 2025](https://www.getdbt.com/blog/data-quality-checks).
- [ ] **8.4 Entity-resolution quality is measured.** Person/institution dedup gets a review queue for low-confidence merges and a reversible merge log, because scraped names vary. *Check:* merges are rows in a table with who/when/why, not destructive updates. Src: (no authoritative standard found; inferred from the provenance model in 6.2).
- [ ] **8.5 Slow-query monitoring via pg_stat_statements, snapshotted** because Neon resets it on suspend. *Check:* a periodic job copies the top N statements by `total_exec_time` into a table. Src: [NE monitor query performance, 2026](https://neon.com/docs/introduction/monitor-query-performance).

## 9. Privacy, security and retention (GDPR / India DPDP)

- [ ] **9.1 OAuth (Gmail) tokens are encrypted at rest with an authenticated cipher (e.g. AES-256-GCM), and the key is held outside the DB** (env/KMS), with a key-version column for rotation. Revoke and delete tokens when no longer needed. *Check:* token columns are `bytea`/ciphertext with a `key_version`, and a revoke-on-disconnect path exists. Src: [Google OAuth 2.0 best practices](https://developers.google.cn/identity/protocols/oauth2/resources/best-practices); [Nylas: storing OAuth credentials (cites OWASP Cryptographic Storage), 2025](https://developer.nylas.com/docs/cookbook/use-cases/build/store-oauth-credentials/); [GDPR Art. 32 (encryption, pseudonymisation)](https://gdpr-text.com/read/article-32/?lang1=en).
- [ ] **9.2 Credential-like URLs (private tab/ballot links, signed URLs, tokens in query strings) are treated as secrets.** Store them hashed or encrypted, strip them from logs, error messages and `COMMENT`s, and never expose them in public pages. *Check:* grep stored `source_url` values for `token=|key=|secret=|sig=`. Src: [OWASP ZAP alert 200014 (sensitive info in URL)](https://www.zaproxy.org/docs/alerts/200014-1/); [PG 18 COMMENT (comments are readable by any user)](https://www.postgresql.org/docs/18/sql-comment.html).
- [ ] **9.3 Every personal-data table has a documented purpose and retention period, and deletion actually runs.** GDPR Art. 5(1)(e) imposes a standing duty to delete or anonymise, not only on request. *Check:* a retention table or registry exists, with a scheduled job per entry. Src: [Legiscope GDPR Art. 5(1)(e), 2025](https://www.legiscope.com/blog/gdpr-article-5-storage-limitation-eur-lex.html); [Thomas Helbing: storage limitation](https://www.thomashelbing.com/en/wissen/dsgvo-hub/einzelthemen/grundsaetze-der-verarbeitung/1.3.3.7-speicherbegrenzung).
- [ ] **9.4 Account deletion cascades through every user-owned row** (tokens, sessions, saved views, rate-limit buckets, user-submitted tags). Scraped public results about the person are handled by a documented policy (suppress or anonymise on request). *Check:* delete a test user, then query every table with a `user_id` FK and find zero rows. Src: [PG 18 constraints (ON DELETE CASCADE)](https://www.postgresql.org/docs/18/ddl-constraints.html).
- [ ] **9.5 India DPDP timeline is tracked.** The DPDP Rules were notified on 14 Nov 2025. The consent-manager rule takes effect 14 Nov 2026. Most substantive obligations, including retention and erasure, take effect 14 May 2027 (some sources say 13 May 2027). *Check:* the privacy notice and erasure flow are in place before May 2027. Src: [Delhi IT Dept OM on DPDP Rules, 2025](https://it.delhi.gov.in/sites/default/files/IT/generic_multiple_files/dpdp_om.pdf); [BDO India DPDP Rules, 2025](https://www.bdo.in/getmedia/87552494-85d2-4edb-95da-0f118fdb3052/The-DPDP-Rules_BDO-India_2025.pdf).
- [ ] **9.6 Audit trail for sensitive actions** (token grant/revoke, data export, deletion, admin merges) goes to an append-only table with actor, action, target and `timestamptz`, and the table holds no secrets. *Check:* the app role has no UPDATE/DELETE grant on the audit table. Src: [GDPR Art. 32 (security of processing)](https://gdpr-text.com/read/article-32/?lang1=en).
- [ ] **9.7 The Postgres rate limiter does not keep raw IPs or emails longer than needed.** Store a hashed or truncated key with TTL cleanup. *Check:* a purge job deletes buckets older than the window. Src: [GDPR Art. 5(1)(e) commentary](https://www.legiscope.com/blog/gdpr-article-5-storage-limitation-eur-lex.html).

## 10. Capacity planning and cost on small managed Postgres

- [ ] **10.1 Size is reported per table, with heap, indexes and TOAST separated.** Use `pg_total_relation_size`, `pg_table_size`, `pg_indexes_size` and `pg_size_pretty`, against the 1 GB Free cap. *Check:* a saved query lists the top 20 relations by total size, and its results are recorded monthly. Src: [PG 18 admin functions](https://www.postgresql.org/docs/18/functions-admin.html); [NE plans](https://neon.com/docs/introduction/plans).
- [ ] **10.2 Headroom alarm before the hard stop.** At the cap, writes fail on Free, so alert at about 70% and have a purge or move-to-object-storage plan ready (5.1, 5.5). *Check:* the alert threshold is documented. Src: [NE FAQ free plan limits, 2026](https://neon.com/faqs/free-plan-limits-and-quotas).
- [ ] **10.3 CU-hours budget: avoid keeping the compute awake.** Pollers such as queue workers, health checks and cron "every minute" jobs prevent scale-to-zero (5 min idle) and burn the 100 CU-h/month. *Check:* the worker poll interval and cron schedule are reconciled against CU-hours in the Neon console. Src: [NE plans](https://neon.com/docs/introduction/plans).
- [ ] **10.4 Bloat on high-churn tables (job queue, rate limiter, sessions) is watched.** Autovacuum triggers at threshold + scale_factor × reltuples. Hot small tables may need per-table `autovacuum_vacuum_scale_factor` lowered. *Check:* `SELECT relname, n_dead_tup, n_live_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC`. Src: [PG 18 routine vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html); [PG 18 monitoring stats](https://www.postgresql.org/docs/18/monitoring-stats.html).
- [ ] **10.5 Queue and limiter tables delete or archive finished rows promptly** rather than growing forever. Consider `DELETE ... WHERE finished_at < now()-interval` on a schedule. *Check:* the row count of the jobs table stays bounded. Src: [PG 18 routine vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html).
- [ ] **10.6 The connection budget respects pooling.** The app uses the `-pooler` (PgBouncer) endpoint from serverless functions, and only migrations and admin tasks use direct. *Check:* `DATABASE_URL` host contains `-pooler`. Src: [Neon blog: Prisma DX improvements, 2024](https://neon.com/blog/prisma-dx-improvements).
- [ ] **10.7 Plan for growth.** Know the Launch pricing ($0.106/CU-h, $0.35/GB-month, storage uncapped, 7-day history) before hitting Free limits. *Check:* a one-line cost estimate at 2× current size. Src: [NE plans](https://neon.com/docs/introduction/plans).

## 11. Naming conventions and documentation

- [ ] **11.1 Lowercase `snake_case` identifiers in the database.** Unquoted names fold to lowercase, and mixed case forces quoting everywhere. Prisma's PascalCase model names should be mapped with `@@map("speaker_score")` and `@map("created_at")`. *Check:* `SELECT table_name FROM information_schema.tables WHERE table_schema='public' AND table_name <> lower(table_name)` returns nothing. Src: [PG wiki Don't Do This, ed. 2024](https://wiki.postgresql.org/wiki/Don't_Do_This); [PG 18 lexical structure](https://www.postgresql.org/docs/18/sql-syntax-lexical.html).
- [ ] **11.2 Identifiers fit in 63 bytes.** Longer names are silently truncated, which bites auto-generated constraint and index names. *Check:* `SELECT conname FROM pg_constraint WHERE length(conname) >= 63`. Src: [PG 18 lexical structure](https://www.postgresql.org/docs/18/sql-syntax-lexical.html).
- [ ] **11.3 Consistent suffixes** (`_id` for FKs, `_at` for timestamptz, `_on` or `_date` for dates, `is_`/`has_` for booleans) and singular *or* plural table names chosen once. *Check:* a naming lint over `information_schema.columns`. Src: (no single authoritative standard found; convention only).
- [ ] **11.4 Tables and non-obvious columns carry `COMMENT ON`.** Describe units (score scale), provenance meaning and retention. Comments are world-readable, so never put secrets in them. *Check:* `SELECT c.relname FROM pg_class c WHERE relkind='r' AND relnamespace='public'::regnamespace AND obj_description(c.oid,'pg_class') IS NULL`. Prisma `///` doc comments do **not** create DB comments, so add COMMENTs in migration SQL. Src: [PG 18 COMMENT](https://www.postgresql.org/docs/18/sql-comment.html).
- [ ] **11.5 Constraint and index names are explicit and meaningful** (`speaker_score_points_range_chk`, `job_pending_idx`), so errors and drift diffs are readable. *Check:* no anonymous `*_check1`-style names in `pg_constraint`. Src: [PG 18 constraints (naming constraints)](https://www.postgresql.org/docs/18/ddl-constraints.html).
