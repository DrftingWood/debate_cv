# Storage sizing for B6 and B9 (2026-10-25)

Groundwork for two owner decisions in `docs/OPUS_TASKS.md`. Nothing here changes code or picks an option.

**Headline:** pre-scraping all 625 corpus tournaments (B9) is about 1.4 million rows and about 375 MB. With a 2x allowance (about 750 MB) it fits the Neon Free limit of 1 GB per project only if production today is under about 250 MB, which is not checked. Storing Tabbycat API JSON as snapshots (B6) adds at most about 100 KB per tournament against today's API mode, and is smaller than the HTML snapshots the HTML mode stores.

## Method

- Bytes per row were measured, indexes included, on a throwaway copy of the local app database (`debate_cv`, seeded from the 73-tournament corpus user) after bulk-inserting synthetic `SpeakerRoundScore` and `JudgeAssignment` rows. Database dropped afterwards.
- Rows per participant come from `corpus_mitra`: 73 tournaments crawled to full round depth, 21,184 participants. Ratios: TeamResult 2.25 (from the seeded app table), SpeakerRoundScore 4.17, JudgeAssignment 1.48, EliminationResult 0.32 (seeded app table), one TournamentParticipant and one ParticipantRole each, Motion 14 per tournament.
- Participant count comes from `corpus2`: participants pages for 582 of the 625 tournaments, 121,376 participants and 52,114 distinct names. Scaled by 625 / 582. The 43 tournaments without a participants page, and any whose tabs return 403, are assumed to be the same average size; 403 tournaments could not be stored at all.
- Neon plan limit: [neon.com/pricing](https://neon.com/pricing), checked 2026-10-25. Free is 1 GB per project. Launch bills storage at $0.35 per GB-month.

Caveats:

- The corpus runs 2018 to 2026. 432 of the 625 carry a 2020 to 2025 year in their name and 141 carry no year, so the B9 window is roughly 260 to 345 MB.
- `JudgeAssignment` is counted for every judge on every panel. Production stores this only for the URL owner unless `EXTRACT_ALL_JUDGES` is set; a pre-scrape that any judge can match against needs all of it.
- The full-depth ratios come from one person's career, mostly Asian and Indian circuit tournaments, averaging 290 participants. That is a biased sample. Allow 2x for that, for index bloat and for growth: about 750 MB, still under 1 GB but with little room left for users, jobs and snapshots.
- Bytes/row include every index the current schema defines on those tables. Snapshots (`SourceDocument`) for the pre-scraped pages are not included. Production's current database size was not checked (no production access from here); it has to be added to these figures.
- On Launch, 0.4 to 0.75 GB costs about $0.15 to $0.30 a month.

Finding for the owner's scope choice: on these numbers the full set fits the free plan, so trimming is a headroom question rather than a fit question, provided production's current size leaves about 250 MB spare.

Open, not measured: the request count and throttle time to crawl 625 tournaments, and the cost of a re-scrape path for corrected tabs.

## B6: snapshot size per tournament

WUDC 2024, the largest tournament in the corpus, fetched once on 2026-10-25. One tournament, so treat it as an upper bound per tournament (625 x 100 KB = at most about 63 MB if every tournament were WUDC-sized; the real figure is far lower):

| Source | Raw | Gzipped (as stored in `bodyGzip`) |
| --- | ---: | ---: |
| API: `teams` | 333 KB | 29.8 KB |
| API: `speakers` | 250 KB | 18.5 KB |
| API: `teams/standings` | 95 KB | 4.3 KB |
| API: `speakers/standings` | 136 KB | 6.3 KB |
| API: `speakers/standings/rounds` | 1,421 KB | 41.1 KB |
| **API, all five** | **2,235 KB** | **100.1 KB** |
| HTML: team tab + speaker tab (stored today) | 1,841 KB | 151.1 KB |

Inserted as `SourceDocument` rows, the five API bodies took 100.9 KB and the two HTML bodies 151.4 KB.

Findings for the owner's choice:

- Options 1 and 2 are the same thing. `bodyGzip` already gzips every stored body, so "compressed" adds nothing.
- Against today's API mode, which stores nothing for these tabs, option 1 adds up to about 100 KB per WUDC-scale tournament under newest-per-URL retention.
- Against HTML mode, which stores the team and speaker tab, it is about two-thirds of the size. So option 1 keeps growth below the level the HTML path already had.
- The 20 Oct report recommended option 1. Nothing here contradicts it; the choice is the owner's.
