# UI/UX standards

Written 2026-10-27; extended the same day with sections 11-14 (UX-44 to UX-87: navigation, tabs, buttons and actions, and wayfinding). This file is the single UI/UX standard for the product; add new rules here rather than starting another file. Forty-three testable rules (UX-1 to UX-43) for every screen in the product, each with a reason, a good and a bad example in this app's own idiom (the "Ledger" system in `docs/DESIGN_INSTRUCTIONS.md` §6), and how it is enforced. A rule with neither a mechanical check nor a reviewer question was cut; the cut list is at the end. The audit that measured the app against these rules is `docs/UI_UX_AUDIT-2026-10-27.md`.

The audit against the navigation, tabs, buttons and wayfinding rules (UX-44 to UX-87) is `docs/UI_UX_AUDIT_NAVIGATION-2026-10-27.md` (findings NV-1 to NV-31).

The owner mentioned a deep-research document on UI/UX standards that was not attached and is not in the repository. These rules were researched from the primary sources listed at the end, read on 2026-10-27. If that document turns up, reconcile it with this one rule by rule rather than replacing either.

These rules apply to **new and changed UI**. They are not a licence to rewrite working screens for style (`CLAUDE.md`, "Out of scope"). They sit beside the code rules in `docs/CODING_STANDARDS.md`; AX-1 to AX-3 there are kept, and the rules below make them specific.

**Baseline.** WCAG 2.2 level AA. WCAG 2.2 is the current W3C Recommendation (updated edition 12 December 2024); WCAG 3.0 is still a Working Draft (latest 10 September 2026) and is not a target.

**Enforcement key.**
- `axe:<rule>` is an axe-core rule run by `npm run a11y` (`scripts/a11y-smoke.mjs`, report-only, both themes, 390 px and 1280 px). Rules axe tags `best-practice` run only with `A11Y_BEST_PRACTICE=1`.
- `smoke:<check>` is a measurement the same script makes itself: `overflowX` (the page scrolls sideways), `targets` (pointer targets under 24×24 px, before axe's spacing exception), `nested` (a link or button inside another), `title` (the document title), `console` (console errors), and the full-page screenshots.
- `lint:<rule>` is ESLint in `npm run lint`. `eslint-config-next` turns on only six `jsx-a11y` rules, all as warnings: `alt-text`, `aria-props`, `aria-proptypes`, `aria-unsupported-elements`, `role-has-required-aria-props`, `role-supports-aria-props`.
- `test` is Vitest in `npm test`.
- `Q` is a question the reviewer asks. Automated checks find a little over half of accessibility issues at best (Deque's study of 13,000 pages found 57% by volume), so most rules keep a question even when a tool also checks them.

None of the `axe` or `smoke` checks block a merge yet; `docs/CI_PLAN-2026-10-27.md` describes how a report-only check becomes blocking.

## 1. Structure and navigation

**UX-1. One `<main>` that holds only page content.** *Why:* screen-reader users jump by landmark, and the skip link (SC 2.4.1) must skip the repeated header, not land above it. *Good:* `<body><a class="skip-link" href="#main"> <header>…</header> <main id="main">…</main> <footer/></body>`. *Bad:* the app header and `Footer` rendered inside `<main id="main">`, so the skip link lands on the header it was meant to skip. *Enforced:* axe `landmark-one-main` and `region` (best-practice tag). Note that axe does not flag today's defect: a `header` inside `main` is simply not a banner, so there is no misplaced banner to report. The question carries this rule. *Q:* "Does Tab, Enter on the skip link put focus on the first thing after the nav?"

**UX-2. Every route has its own title; error states start with "Error:"; every `<html>` has `lang`.** *Why:* the title is the first thing announced (SC 2.4.2); the GOV.UK error-summary pattern prefixes it so the failure is heard before anything else; `lang` sets pronunciation (SC 3.1.1). *Good:* `export const metadata = { title: 'Sharing' }` on `/settings/sharing` → "Sharing · debate cv". *Bad:* all four settings pages titled "Settings · debate cv"; `app/global-error.tsx` rendering `<html>` without `lang`. *Enforced:* axe `document-title`, `html-has-lang`; smoke `title` lists each page's title so duplicates show; *Q:* "Does the new route export a title that differs from its siblings?"

**UX-3. One `h1` per page and no skipped heading levels.** *Why:* heading navigation is the most common way screen-reader users scan a page (SC 1.3.1, 2.4.6). *Good:* `EmptyState` given a `headingLevel` so it renders `h2` straight under the page `h1`. *Bad:* the settings layout's `h2` "Settings" above each settings page's `h1`; `EmptyState` hard-coding `h3` directly after an `h1`. *Enforced:* axe `page-has-heading-one`, `heading-order` (best-practice); *Q:* "Read the headings alone, in order: is the outline right?"

**UX-4. The current page is marked once per nav.** *Why:* `aria-current="page"` is the only way the active pill is announced. *Good:* `NavLink` sets it from the pathname, with `exact` on `/cv` so Record and Statistics never both claim it. *Bad:* the dashboard's filter tile and filter chip both setting `aria-current="page"` for the same URL. *Q:* "In each nav, does exactly one link say it is current?"

**UX-5. Menus and popovers use the disclosure pattern.** *Why:* `role="menu"` promises arrow-key navigation and typeahead (APG menu-button); the APG's own site-navigation example deliberately avoids it. A button with `aria-expanded` that shows a list of links needs no promise it cannot keep. *Good:* `<button aria-expanded={open} aria-controls="account-panel">` then `<div id="account-panel"><ul><li><Link/></li></ul></div>`, focus moved to the first link on open and back to the button on Escape. *Bad:* `NotificationBell`'s `role="menu"` wrapping a heading `div` and plain links (no `menuitem` children, which axe flags). *Enforced:* axe `aria-required-children`; *Q:* "Does the popover open, close on Escape, and return focus with the keyboard alone?"

**UX-6. Modal dialogs are named, trap focus, close on Escape and return focus.** *Why:* APG dialog (modal) pattern; without the trap, Tab walks into the page behind the overlay. *Good:* `CvRowReportButton`: `aria-modal`, focus to the first checkbox, Tab wraps, Escape closes, focus returns to the row's Report button. *Bad:* a delete-account confirmation that unmounts the trigger and leaves focus on `<body>`. *Enforced:* axe `aria-dialog-name`; *Q:* "Open it, press Tab twenty times, press Escape: where is focus?"

**UX-7. When an action replaces the control that had focus, move focus to the new content.** *Why:* SC 2.4.3; a keyboard or screen-reader user otherwise restarts from the top of the page with no word of what changed. *Good:* each onboarding step's `h2` has `tabIndex={-1}` and is focused when `phase` changes. *Bad:* "Continue" in `OnboardingFlow` swapping the whole card so the button that had focus no longer exists. *Q:* "After the click, where is focus, and was the change announced?"

## 2. Interaction

**UX-8. Pointer targets are at least 24×24 CSS px; primary controls are 44 px on touch.** *Why:* SC 2.5.8 sets 24 px (or 24 px of clear spacing) at AA; Apple asks 44×44 pt and Material 48×48 dp for touch. The repo's `coarse:` variant already raises `Button` to 44 px on a coarse pointer. *Good:* `<Button size="sm">` (32 px, 44 px under `coarse:`). *Bad:* `<Button variant="link" size="sm">` for the dashboard's per-row "Ingest" and "Clear", which skips the size classes entirely (18 px tall, 4 px apart); the toast's dismiss `×` at 16 px. *Enforced:* axe `target-size`; smoke `targets` counts every control under 24 px; *Q:* "Is any new control smaller than 24 px, or closer than 24 px to its neighbour?"

**UX-9. No interactive element inside another.** *Why:* `<a><button>` is invalid HTML, makes two tab stops for one action, and is announced as "link, button". *Good:* a `buttonClasses({ variant, size })` helper exported from `components/ui/Button.tsx`, applied to the `<Link>` itself. *Bad:* `<Link href="/dashboard"><Button>Open imports</Button></Link>` (12 places today). *Enforced:* smoke `nested` counts `a button`, `a a`, `button a` and `button button` on every checked page. axe's `nested-interactive` only looks inside button-like widgets, and it did not flag any of the twelve cases in the 2026-10-27 run. *Q:* "Is there a `<Button>` inside a `<Link>` or an `<a>`?"

**UX-10. Focus is always visible.** *Why:* SC 2.4.7; `globals.css` already draws a 2 px `:focus-visible` outline in `--ring` and the only way to lose it is to switch it off. *Good:* leave the global outline alone, or `focus-visible:ring-2 focus-visible:ring-ring` (7:1 against the canvas). *Bad:* `outline-none focus:ring-2 focus:ring-primary/20`, about 1.2:1, so the ring is invisible. *Q:* "Does the change add `outline-none`? What replaces it, at what contrast?"

**UX-11. Accessible names contain the visible label and say which row.** *Why:* SC 2.5.3 (speech users say what they see) and SC 2.4.6; thirty buttons all named "This is me" cannot be told apart in a screen reader's controls list. *Good:* `aria-label={`Report a problem with ${tournamentName}`}` on the icon-only report button. *Bad:* the sharing switch named "Toggle public sharing" beside the visible text "Public sharing"; "Find me" repeated on every unmatched row. *Enforced:* axe `button-name`, `link-name` (and `label-content-name-mismatch`, an experimental rule); *Q:* "Read the controls list: is every name unique and does it start with the visible words?"

**UX-12. Toggles expose state and keep a fixed label.** *Why:* SC 4.1.2; APG switch and toggle-button patterns say the label must not change with the state, or the user cannot tell whether it names the state or the action. *Good:* `<button aria-pressed={mineOnly}>Only me</button>`. *Bad:* `VerifyMineOnlyToggle` flipping its text between "Only me" and "Everyone" with no `aria-pressed`. *Enforced:* lint `jsx-a11y/role-has-required-aria-props` (catches `role="switch"` without `aria-checked`); *Q:* "Does the control say whether it is on, without its text changing?"

## 3. Forms

**UX-13. Every field has a visible label; option groups have a legend.** *Why:* SC 1.3.1, 3.3.2 and 4.1.2; a placeholder disappears as soon as the user types and is not reliably announced. *Good:* `CvRowReportButton`'s `<fieldset><legend>What looks wrong?</legend>` and `<label htmlFor="report-comment-…">`. *Bad:* the delete-account field whose only label is a placeholder containing the email. *Enforced:* axe `label`, `select-name`; *Q:* "Cover the placeholder: can you still tell what the field is for?"

**UX-14. Personal-data fields carry `autocomplete`; slug and email fields switch off autocapitalise and spellcheck.** *Why:* SC 1.3.5, and a phone capitalising "Maya-rao" makes a valid slug fail validation. *Good:* `<input autoComplete="off" autoCapitalize="none" spellCheck={false}>` on the public-CV slug; `autoComplete="email"` on an email field. *Bad:* the slug input with neither. *Enforced:* axe `autocomplete-valid`; *Q:* "What does a phone keyboard do to the first letter typed here?"

**UX-15. Field errors are text next to the field, linked to it, with focus moved there.** *Why:* SC 3.3.1 and 3.3.3; GOV.UK's error-message pattern (error after the hint, `aria-describedby`, visually hidden "Error:" prefix, error summary at the top when there are several). A toast disappears in five seconds, sits far from the field and cannot be linked to it; NN/g calls toasts "a bad way to implement an error message". *Good:* `<input aria-invalid aria-describedby="slug-hint slug-error">` then `<p id="slug-error" className="text-caption text-destructive">That address is taken. Try maya-rao-2.</p>`. *Bad:* `SharingManager` reporting "slug_taken" only through `toast.show({ kind: 'error' })`. *Q:* "Submit it wrong: is the error next to the field, does it say how to fix it, and is focus on it?"

**UX-16. Do not disable submit to signal bad input.** *Why:* a disabled button cannot be focused and does not say why it is disabled (GOV.UK button guidance: avoid disabled buttons); validate on submit (GOV.UK validation pattern). Disabling while a request is in flight is fine (`loading`). *Good:* "These are me — continue" stays enabled; pressing it with nothing ticked shows "Tick at least one name that is you" under the list. *Bad:* the same button disabled at zero, so the helpful message written for that case can never appear. *Q:* "If the button is disabled, where on screen does it say why?"

**UX-17. Destructive actions confirm, name the consequence, default to safety and cannot double-submit.** *Why:* NN/g heuristic 5 (error prevention), SC 3.3.4's intent for data changes, GOV.UK's warning-button guidance (add a confirmation step; do not rely on red alone). *Good:* "Disconnect Gmail? New tournaments stop arriving. Your record stays and you stay signed in." with focus on Cancel and `loading` on the confirm button. *Bad:* `IdentityManager` saving an empty selection that removes every claimed tournament with no confirmation. *Q:* "What is lost if this is clicked by mistake, and does the screen say so before it happens?"

**UX-18. Field and control boundaries reach 3:1.** *Why:* SC 1.4.11; the hairline `border-border` token is `--border` at 16% (1.25:1 on white in light, 1.56:1 in dark), right for table rules and wrong for the edge of a text box. *Good:* a field border at `hsl(var(--border) / 0.5)` or stronger (about 3:1 in light; check dark separately), or `border-input` once that token is raised. *Bad:* `border border-border bg-paper` on the slug and delete-confirmation inputs; a switch whose off track is `bg-ink/10`. *Q:* "Squint: can you see where the field is before you click it, in both themes?"

## 4. Feedback and status

**UX-19. One polite live region, present at load; `role="alert"` for errors; no nesting; no polling regions.** *Why:* SC 4.1.3; live regions must exist before their content changes (Soueidan; Roselli); a region inside a region is announced twice or not at all; `aria-live` on a section that re-renders every five seconds talks over everything else. *Good:* the toast viewport as a single `role="status"` container; each card a plain `div`. *Bad:* `aria-live="polite" aria-atomic="true"` on the toast viewport plus `role="status"` or `role="alert"` on each card inside it (and `aria-atomic` re-reading every toast when one is added); `IngestProgressTracker`'s whole section `aria-live` while it polls. *Q:* "Turn on a screen reader: is each message read exactly once?"

**UX-20. Toasts carry passive success only; errors and actions persist.** *Why:* SC 2.2.1 (a time limit must be adjustable; a five-second toast is one); the APG alert pattern ("avoid designing alerts that disappear automatically"); Material says snackbars with an action stay until acted on. *Good:* "Link copied" as a 5 s toast that pauses on hover and focus. *Bad:* "Scan failed", "Report not sent" and the "View your CV" action link all auto-dismissing after 5 s. *Q:* "If the user looked away for ten seconds, what did they miss?"

**UX-21. A harmless wait is a neutral notice with the time remaining.** *Why:* NN/g heuristics 1 and 9; labelling a cooldown "failed" sends the user looking for a fault that does not exist. The server already sends `Retry-After`. *Good:* an info notice "Your mailbox was scanned a moment ago. You can scan again in 1:42." with the button disabled and counting down, re-enabled at zero. *Bad:* `DashboardActions.ScanButton` throwing the friendly cooldown text into an error toast headed "Scan failed". *Enforced:* `tests/ingest.scanErrorMessage.test.ts` (extend it to cover the kind and the wait); *Q:* "Is anything here called an error that the user cannot and need not fix?"

**UX-22. Long work shows "X of N", can be cancelled, and has a named progressbar.** *Why:* NN/g response-time limits (past 10 s, show percent done and offer a way out); the progressbar needs a name (axe). *Good:* "Ingesting… 7/23" with a Stop button, and `role="progressbar" aria-label="Import progress"`. *Bad:* a `role="progressbar"` with no name. *Enforced:* axe `aria-progressbar-name`; *Q:* "If this takes two minutes, what does the user see, and can they stop it?"

**UX-23. Raw codes never reach the screen.** *Why:* NN/g error-message guidelines (plain language, the specific problem, a next step); GOV.UK says never "An error occurred". *Good:* a mapping helper beside `scanErrorMessage` that turns `bad_request`, `unauthorized`, `HTTP 500` into a sentence and an action. *Bad:* `description: result.error` printing `rate_limited` or the first 200 characters of an HTML error page; "Could not load sharing (HTTP 500)". *Enforced:* a unit test per mapping helper; *Q:* "Could this text contain a code, a URL path or a stack trace?"

## 5. Empty, loading and error states

**UX-24. Every list or table defines its empty state.** *Why:* NN/g on empty states: say why it is empty and give a direct path to fill it; never show "no records" while still loading. "Nothing matches this filter" is a different state from "nothing yet". *Good:* "No tournaments ingested yet. Scan Gmail finds the links, then Ingest all parses each one." with an "Open imports" action. *Bad:* the public CV rendering only its header when sharing is on and there are no rows; onboarding staying on the scan step with a 5 s toast when the scan finds nothing. *Q:* "What does this look like with zero rows, and with zero rows after a filter?"

**UX-25. Loading screens mirror the page, use fluid widths and announce once.** *Why:* NN/g: skeletons for full-page loads under 10 s; skeletons are `aria-hidden`, so without a status line a screen-reader user hears nothing. A fixed-width skeleton bar wider than the phone makes the page scroll sideways while it loads. *Good:* `loading.tsx` with `w-full max-w-sm` bars and `<p role="status" className="sr-only">Loading statistics…</p>`. *Bad:* `w-96` skeleton bars (384 px) in a 390 px viewport; a 4-column skeleton for a table that has 3. *Enforced:* smoke `overflowX` (catches it on slow loads); *Q:* "Does the skeleton have the same shape as the page, and does a screen reader hear 'Loading'?"

**UX-26. Error boundaries speak plain language and give a reference, a retry and a way out.** *Why:* NN/g heuristic 9; Next.js passes `error.digest` precisely so the user can quote it without seeing internals. *Good:* "This page did not load. Try again, or go to your record. Reference: 3c9f…" *Bad:* `{error.message}` rendered verbatim in `app/error.tsx`. *Q:* "What does this screen show for a thrown Prisma error?"

**UX-27. No blank numeric cell; a real state gets a word.** *Why:* Ledger §6: an em dash means "the source did not publish this"; a blank reads as a bug. Using the same dash for a real outcome hides that outcome. *Good:* `<Nil />` for a speaker score the tab did not publish; "Did not break" in `text-ink-soft` in the Result column. *Bad:* `<Nil />` for "did not break" on the public CV. *Q:* "Can every dash on this screen be read as 'not published'?"

## 6. Tables

**UX-28. Tabular data uses `DataTable` with proper headers and a name.** *Why:* SC 1.3.1; WAI tables tutorial; APG: use a native table whenever possible, and grid only for interactive cells. Row headers let a screen reader announce "Worlds 2025, Speaker avg 76.4" instead of a bare number. *Good:* `<Table label="Speaking record by tournament">` with `<Th>` (which sets `scope="col"`) and a `<Th scope="row">` first cell. *Bad:* the dashboard's raw `<table className="ledger">` with bare `<th>` and no name. *Enforced:* axe `th-has-data-cells`, `td-headers-attr`; `CODING_STANDARDS.md` AX-1; *Q:* "Is this built on `DataTable`, and does each row have a header cell?"

**UX-29. Wide tables scroll inside a focusable, named region with a visible cue.** *Why:* SC 2.1.1: a keyboard user cannot scroll a region that holds no focusable element unless the region itself takes focus (axe `scrollable-region-focusable`, serious). The Ledger rule says the page body never scrolls sideways. The July audit found the public CV hiding its Result column behind an unmarked scroll. *Good:* `TableScroll` rendering `<div role="region" aria-label={label} tabIndex={0} className="table-scroll">` with CSS scroll shadows on any edge that has more content. *Bad:* a bare `overflow-x-auto` div around a `min-w-max` table. *Enforced:* axe `scrollable-region-focusable`; smoke `overflowX`.

**UX-30. Below `md`, a wide table becomes cards; nothing is truncated away.** *Why:* NN/g on mobile tables (lock the first column, show that more is available, or switch layout); SC 1.4.10. A phone is the primary device (`DESIGN_INSTRUCTIONS.md` §6, Layout). *Good:* `/cv`'s speaking cards: one `panel` per tournament with a `dl` of labelled figures. *Bad:* the public CV rendering its desktop table at 390 px; mobile `dd` values with `truncate` whose full text exists only in `title`. *Enforced:* smoke screenshots at 390 px; *Q:* "At 390 px, can every value be read without hovering or scrolling sideways?"

**UX-31. Numeric columns are `.cell-num`; headers carry their unit.** *Why:* Ledger rule 2 (figures are mono and tabular, aligned down the page); a header that hides its unit in a tooltip misleads (SC 1.3.1, 2.4.6). *Good:* `<Th numeric>vs you (pp)</Th>` beside `<Th numeric>vs you (pts)</Th>`. *Bad:* two columns both headed "vs you", one in percentage points and one in speaker points. *Q:* "Is every number right-aligned in mono, and is its unit in the visible header?"

## 7. Charts and figures

**UX-32. Every chart has a text alternative.** *Why:* SC 1.1.1; W3C complex-images tutorial (short alternative plus long description or data table); the GOV.UK Analysis Function asks for alt text or a data table on every chart. *Good:* `<svg role="img" aria-labelledby="t d"><title id="t">Speaker average by season</title><desc id="d">2023: 74.1 (n=18) … 2026: 77.0 (n=9)</desc>`. *Bad:* the score histogram as loose `div`s with the bin ranges only in `title`. *Enforced:* axe `svg-img-alt`, `role-img-alt`; *Q:* "With the screen off, what does a screen reader say this chart shows?"

**UX-33. Chart text reaches 4.5:1 and marks 3:1, at a legible rendered size.** *Why:* SC 1.4.3 and 1.4.11; the Analysis Function asks 4.5:1 for all chart text. An SVG with a fixed 640-unit `viewBox` scaled to a 326 px panel draws "12 px" labels at about 6 px. *Good:* `fill="hsl(var(--muted-foreground))"` on `<text>` (5.3:1 light, 6.0:1 dark); opacity only on gridlines. *Bad:* `fill="currentColor" fillOpacity={0.38}` on the `n=` line (about 2.1:1); histogram bars at `bg-ink/15` (about 1.3:1). *Enforced:* axe `color-contrast` (it checks SVG text only partly); *Q:* "Screenshot at 390 px: can you read the smallest label?"

**UX-34. Colour is never the only cue; on a number it means up or down.** *Why:* SC 1.4.1 and Ledger rule 3: green up or kept, red down or lost, gold a break, blue analysis, amber attention, emerald the one brand accent. *Good:* `DeltaChip` pairing `val-pos` with ▲ and "+2.8"; `val-flat` for a delta that rounds to zero. *Bad:* a green "−0.0"; gold on a "Pro ×N" badge that is not a break; a rejected tag in `text-oxblood` (the emerald accent). *Q:* "Name the claim each colour on this screen is making."

**UX-35. The sample size is visible next to every aggregate.** *Why:* `DESIGN_INSTRUCTIONS.md` §9 rule 1 ("a 100% win rate over two rounds is not a statistic"); thin samples are marked in text and use the same threshold as the findings engine (`MIN_QUIRK_ROUNDS`). *Good:* `TeammatesSection` printing `n = 2` instead of a win rate for a thin row. *Bad:* the thin-sample "·" marker at 50% opacity with its round count only in `title`; `StatsSplitTable` defaulting `thinBelow` to 4 while findings need 6. *Q:* "Next to each percentage or average, where is the n?"

**UX-36. Nothing needed lives only in a `title` or on hover.** *Why:* SC 1.4.13; touch devices never show `title`, and keyboard users rarely get it. *Good:* `/cv`'s visible paragraph explaining "Team rank", "Spk avg" and "Spk tab" under the table. *Bad:* team placement "#3 of 40 · top 8%" only in a `title`; truncated tournament names on mobile cards with no way to read them in full. *Q:* "On a phone, is every piece of information on this screen reachable?"

## 8. Visual design

**UX-37. Text reaches 4.5:1 (3:1 for large text) in both themes.** *Why:* SC 1.4.3. The tokens pass on their own (in light, `muted-foreground` is 5.3:1 on a card; in dark, 6.0:1). They fail as soon as an opacity modifier is added: `text-ink-soft/50` is about 2.0:1. *Good:* `text-ink-soft` at full strength for secondary text. *Bad:* `text-ink-soft/50`, `opacity-60` on text. *Enforced:* axe `color-contrast`, run in both themes by `npm run a11y`.

**UX-38. Every surface is themed in light and dark.** *Why:* contrast applies to whatever the user is shown; MDN's `color-scheme` makes native form controls and scrollbars follow the theme. *Good:* `[data-theme='dark'] { color-scheme: dark; }` beside the dark tokens; prose colours mapped to tokens. *Bad:* `prose prose-stone` on `/privacy` and `/terms` (fixed stone greys on the graphite canvas); the OG image and `global-error.tsx` still in the old editorial palette. *Enforced:* axe `color-contrast` (dark run); smoke screenshots in dark; *Q:* "Did you look at it in dark?"

**UX-39. No sideways page scroll at 320 CSS px.** *Why:* SC 1.4.10 (reflow) and the Ledger rule "the page body must never scroll sideways". *Good:* `flex-wrap` on header button groups; `grid-cols-2 sm:grid-cols-4`. *Bad:* `/admin/tags`'s four `nowrap` buttons in one `justify-between` row. *Enforced:* smoke `overflowX` at 390 px (run with a 320 px viewport before shipping a new layout); *Q:* "Did you check 320 px?"

**UX-40. All motion honours `prefers-reduced-motion`.** *Why:* MDN `prefers-reduced-motion`; WCAG technique C39 (for SC 2.3.3, AAA, adopted here because the guard already exists in `globals.css`). CSS animations are covered by that guard; JavaScript `scrollTo({ behavior: 'smooth' })` is not. *Good:* `behavior: matchMedia('(prefers-reduced-motion: reduce)').matches ? 'auto' : 'smooth'`. *Bad:* `PageJumpNav`'s back-to-top button always smooth-scrolling. *Q:* "With reduce motion on in the OS, does anything still slide?"

## 9. Performance

**UX-41. Core Web Vitals at the 75th percentile: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1.** *Why:* web.dev's "good" thresholds, unchanged since INP replaced FID in March 2024. A stats page that shifts as charts load, or a filter chip that takes half a second to respond, is felt before it is measured. *Good:* skeletons with the real layout's dimensions (no shift when data arrives); `next/font` with `display: swap` (already in `app/layout.tsx`). *Bad:* a client-side filter that re-renders 900 lines of stats on every click. *Q:* "Did a Lighthouse mobile run, or Vercel Speed Insights, show any of the three outside 'good' on the changed page?"

## 10. Copy

**UX-42. Copy uses the IA's names and the debater's words.** *Why:* NN/g heuristic 2 (match the real world) and heuristic 4 (consistency); `DESIGN_INSTRUCTIONS.md` §5 and §8. *Good:* "Imports", "Record", "Reconnect Gmail. Your record stays." *Bad:* "Find yourself on the dashboard", page title "My CV", "Ingest jobs", "queue drains", "Revoke the OAuth grant", "Tournaments in flight" over four zeroes. *Q:* "Would a second-year debater understand every word without knowing how the app is built?"

**UX-43. A link that opens a new tab says so.** *Why:* WCAG advisory technique G201; an unexpected new tab breaks the Back button (SC 3.2.5's intent). *Good:* `<ExternalLink aria-hidden />` visible, plus `<span className="sr-only"> (opens in new tab)</span>`. *Bad:* the tournament-name links on `/cv`, whose icon is `opacity-0` until hover and has no text. *Q:* "Does every `target="_blank"` say so, visibly and to a screen reader?"

## How to read sections 11-14

Sections 11-14 were researched on 2026-10-27 for navigation, tabs, buttons and wayfinding. Each rule adds two fields to the format above:

- *Source:* the page the rule rests on, with its URL. Every source was opened on 2026-10-27 unless it says "(search result)", which means the wording was seen in a search-engine result or an official mirror because the page itself renders only with JavaScript (Apple HIG, Material 3). The full list is under "Sources for sections 11-14" at the end.
- *Severity:* the priority an audit finding against the rule should get, on the audit's scale (`docs/UI_UX_AUDIT-2026-10-27.md`): P0 blocks a task or is a clear WCAG A/AA failure on a core path; P1 a significant defect; P2 moderate; P3 polish.

**The app these rules are for.** A data-dense, desktop-first reference tool that people also open on a phone between rounds at a tournament. Four signed-in destinations (Record, Statistics, Imports, Settings, plus Admin for operators), a section nav inside `/cv` and inside `/settings`, and two shells without app chrome (landing, public CV). Where sources disagree, the decision is recorded in "Where the sources disagree" after section 14, with the reason it fits this app.

## 11. Navigation

**UX-44. Primary navigation stays visible.** On desktop the section links sit across the top bar; on phones they stay on screen as a visible strip. A hamburger or "Menu" button is not used while there are five or fewer destinations. *Why:* NN/g's study of 179 users found hidden navigation was used in 27% of desktop cases against 48% for visible navigation, and made tasks slower and harder on both platforms; NN/g's advice is to keep up to four links visible on mobile, and its 2024 menu checklist opens with "show navigation on larger screens". A side rail is for many or growing categories (NN/g, vertical navigation), which four destinations are not. *Good:* `app/(app)/layout.tsx` today: links in the desktop header, and below `md` a second row "rather than collapsing into a hamburger". *Bad:* a `<button aria-label="Menu">` that hides Record and Imports on a phone. *Source:* NN/g, "Hamburger Menus and Hidden Navigation Hurt UX Metrics" (2016), https://www.nngroup.com/articles/hamburger-menus/; NN/g, "Menu-Design Checklist" (2024), https://www.nngroup.com/articles/menu-design/; NN/g, "Left-Side Vertical Navigation on Desktop" (2021), https://www.nngroup.com/articles/vertical-nav/. *Q:* "At 390 px and at 1280 px, can every section be reached in one tap with nothing opened first?" *Severity:* P1 if a core section is hidden behind a menu on a phone; P2 on desktop admin-only pages.

**UX-45. At most five top-level destinations, in the same order on every page.** Items that appear only for some users (Admin) or some states go at the end, so the others never shift. *Why:* SC 3.2.3 (AA) requires repeated navigation in the same relative order; inserting or removing items is allowed, reordering is not. Material's navigation bar is for two to five destinations, and NN/g notes that past five it is hard to keep touch targets large enough. *Good:* Record · Statistics · Imports · Settings · Admin, with Admin appended last. *Bad:* putting Admin second for operators so every other item moves along. *Source:* WCAG 2.2 Understanding 3.2.3, https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html; NN/g, "Basic Patterns for Mobile Navigation" (2015), https://www.nngroup.com/articles/mobile-navigation-patterns/; Material 3 navigation bar (search result via SAP Fiori's Material mirror), https://www.sap.com/design-system/fiori-design-android/v26-4/components/m3-standard-components/navigation-bar/usage. *Q:* "Is a sixth top-level item being added? Which existing one does it replace or move under?" *Severity:* P1 if the order changes between pages (an AA failure); P2 for a sixth item.

**UX-46. Nav labels are one or two plain words, always as text.** Use the IA's names (UX-42), front-load the meaning, keep one case style, and never show a nav item as an icon alone. The label matches the page's `h1` closely enough that a user who clicked "Imports" lands on a page headed "Imports". *Why:* NN/g menu checklist guidelines 7 and 8 (familiar wording, easy to scan); NN/g vertical-nav and icon-usability articles warn against icon-only labels; SC 2.4.6 (headings and labels describe the topic). *Good:* "Imports" in the nav and "Imports" as the `h1`. *Bad:* a nav item "Dashboard" leading to an `h1` "Your imports", or a gear icon standing in for "Settings". *Source:* https://www.nngroup.com/articles/menu-design/; NN/g, "Icon Usability" (2014), https://www.nngroup.com/articles/icon-usability/. *Q:* "Read the nav, then the `h1` of each page it opens: are they the same words?" *Severity:* P2; P3 for case inconsistency.

**UX-47. Every page shows where the user is, with two cues.** Each nav level that contains the current page marks exactly one item `aria-current="page"` (UX-4). A page with no item of its own in a nav level marks its parent instead (`/cv/motions` lights the header's "Record"). The current item differs from the others in at least two ways (for example a filled pill and a heavier weight), never by a faint tint alone. *Why:* NN/g calls failing to show the current location "probably the single most common mistake" in menus (checklist guideline 5); NN/g's tabs guidance asks for at least two selection indicators; SC 1.4.1 forbids colour as the only cue and SC 1.4.11 asks 3:1 for the indicator. *Good:* the settings side nav's `bg-primary-soft text-primary` pill (a fill and a colour change), with a weight change added so it survives greyscale. *Bad:* the header's `NavLink`: Record is `exact` and Statistics matches only `/cv/stats*`, so on `/cv/motions`, `/cv/tags` and `/cv/verify` no header item is current; and its only cue is the `bg-surface-2` tint. *Source:* https://www.nngroup.com/articles/menu-design/; NN/g, "Tabs, Used Right" (2024), https://www.nngroup.com/articles/tabs-used-right/; W3C APG disclosure navigation example, https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/. *Q:* "Open every route: in each nav, which item is lit, and could you tell in greyscale?" *Severity:* P2; P1 if no level marks the current page at all.

**UX-48. A destination lives in one nav level; a section nav belongs to its page.** Do not repeat a destination in both the header and a section nav unless both mark it current together. A section nav (CV sections, Settings sections) sits inside `<main>`, directly under the page `h1`, so the skip link passes the header but not it. *Why:* duplicated destinations split "you are here" across two bars (UX-47) and add tab stops; NN/g's tabs article says navigation tabs and in-page tabs must not be mixed in one control. *Good:* the header holds the four sections; `CvSubNav` holds the pages inside Record. *Bad:* "Record" and "Statistics" appear in both the header and `CvSubNav`, and on `/cv/motions` only the sub-nav says where the user is. *Source:* https://www.nngroup.com/articles/tabs-used-right/; https://www.nngroup.com/articles/menu-design/. *Q:* "Does any link on this page appear in two navs? Do both agree it is current?" *Severity:* P2.

**UX-49. Navigation is links in a labelled `<nav>`, nothing more.** No `role="menu"`, `menubar`, `tablist` or `tab` on site navigation, whatever it looks like. A dropdown of links is the disclosure pattern (UX-5). *Why:* the APG's own site-navigation example avoids the menu role "because it does not provide the complex functionality that assistive technologies expect"; a tablist promises arrow-key movement and a panel on the same page, and a screen reader user who hears "tab 2 of 5" does not expect the URL to change. Consensus in WebAIM's list and in public design systems is the same: tab-styled navigation is a list of links in a `nav`. *Good:* `CvSubNav`: `<nav aria-label="CV sections">` of `<Link aria-current>`. *Bad:* adding `role="tablist"` to `CvSubNav` because it looks like a segmented control. *Source:* https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/; W3C APG menu button, https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/; WebAIM list thread (search result), https://webaim.org/discussion/mail_message?id=38884. *Enforced:* axe `aria-required-children` catches a `menu` or `tablist` without the right children. *Q:* "Does this nav change the URL? Then which ARIA role is on it, and why?" *Severity:* P1 (it misleads screen-reader users on every page).

**UX-50. One skip link, first in the tab order, visible on focus, landing on `<main>`.** Anything repeated on every page (header, primary nav, breadcrumbs, back links) comes before `<main>` so the skip link passes it; page-specific navigation (UX-48) comes after. *Why:* SC 2.4.1 (A); WebAIM: the skip link must be among the first items, "become prominently visible when it is focused", and move focus to the main content; GOV.UK places breadcrumbs and back links "before the `<main>` element" for the same reason. *Good:* `<a class="skip-link" href="#main">` as the first child of `<body>`. *Bad:* a skip link hidden with `display:none` (not focusable), or one that lands on the header (UX-1). *Source:* WebAIM, "Skip Navigation" Links, https://webaim.org/techniques/skipnav/; GOV.UK back link, https://design-system.service.gov.uk/components/back-link/; GOV.UK breadcrumbs, https://design-system.service.gov.uk/components/breadcrumbs/. *Q:* "Load the page, press Tab once: is the skip link visible? Press Enter, then Tab: is focus on the first thing in the page?" *Severity:* P1 if missing or broken.

**UX-51. Landmarks are top-level and uniquely named; all content is inside one.** `banner`, `main` and `contentinfo` appear once each and are not nested in anything; more than one `nav` gets distinct labels without the word "navigation" ("Sections", "CV sections", "Settings sections"). Two navs with identical links may share a label (the desktop and phone copies of the header nav). *Why:* APG landmark regions: "banner, main, complementary and contentinfo landmarks should be top level landmarks"; "if a page includes more than one navigation landmark, each should have a unique label"; a label of "Site navigation" is read as "site navigation navigation". *Good:* the current header: two `nav aria-label="Sections"`, only one visible at a time. *Bad:* a `<nav aria-label="Main navigation">`; a dialog's content wrapped in a landmark. *Source:* W3C APG, Landmark Regions, https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/. *Enforced:* axe `region`, `landmark-unique`, `landmark-no-duplicate-banner` (best-practice). *Q:* "List the landmarks in a screen reader's rotor: does each have a distinct, short name?" *Severity:* P2.

**UX-52. No breadcrumbs; a back link only where Back would lose the user's place.** The app is two levels deep (section, then page), and every page is already reachable from a visible nav, so breadcrumbs add a third bar that repeats the other two. A back link ("Back to Imports") belongs only on a detail page reached from a filtered list, and it must return to that list in the state the user left it. *Why:* NN/g: skip breadcrumbs on shallow sites; GOV.UK: breadcrumbs are for "multiple levels of a website" and never combine with a back link; GOV.UK back link: "takes users to the previous page they were on, in the state they last saw it". *Good (proposed):* a future detail page linking "Back to imports" to `/dashboard?filter=failed` when that was the list the user came from. *Bad:* a back link that calls `router.back()` and sends a user who arrived from an email to the email client. *Source:* NN/g, "Breadcrumbs: 11 Design Guidelines" (2018, reviewed 2026), https://www.nngroup.com/articles/breadcrumbs/; https://design-system.service.gov.uk/components/breadcrumbs/; https://design-system.service.gov.uk/components/back-link/; APG breadcrumb, https://www.w3.org/WAI/ARIA/apg/patterns/breadcrumb/. If breadcrumbs are ever added (a third level appears), follow APG: a `nav` named "Breadcrumb", the current page last, not a link, with `aria-current="page"`. *Q:* "Where does this back link go if the page was opened from a bookmark?" *Severity:* P2.

**UX-53. Account and utility controls sit top right, after the section links, in a fixed order.** Theme, notifications, then the account menu, on every signed-in page. Sign out lives in the account menu, labelled "Sign out". Utilities are visibly secondary to the section links. *Why:* NN/g: utilities belong "where people expect them", the top right, with less visual weight than the main navigation; icons used for utilities need text labels because hover tooltips do not exist on touch; SC 3.2.3 for the fixed order. *Good:* `ThemeToggle`, `NotificationBell`, `UserMenu`, in that order, on every page. *Bad:* "Sign out" placed in the footer on some pages and in the account menu on others. *Source:* NN/g, "Utility Navigation" (2015), https://www.nngroup.com/articles/utility-navigation/; https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html. *Q:* "Is sign-out in the same place on every page, reachable in two taps on a phone?" *Severity:* P2.

**UX-54. The signed-out shell offers only what a visitor can open; the public CV has no app chrome.** Signed-out navigation is Sample CV, Privacy and the sign-in call to action (DESIGN_INSTRUCTIONS §5). `/u/[slug]` is a document someone was sent: no app nav, no account menu, one link back to the product. *Why:* a link that redirects to sign-in is a dead end for a visitor (NN/g heuristic 3, user control); the public CV is read by judges and convenors who are not users. *Good:* `SectionLinks` rendering three visitor links when signed out. *Bad:* a signed-out header that still offers "Imports" and bounces to `/`. *Source:* DESIGN_INSTRUCTIONS §5; NN/g, 10 heuristics, https://www.nngroup.com/articles/ten-usability-heuristics/. *Q:* "Signed out, does every link in the header open a page rather than a redirect?" *Severity:* P2.

**UX-55. A horizontally scrolling nav strip shows it continues and keeps the current item in view.** When a nav strip overflows on a phone, the cut edge fades or shows an arrow, and on load the current item is scrolled into view, not left off-screen. *Why:* hidden overflow raises interaction cost and hides options (NN/g tabs: keep the number of tabs low; Carbon tabs scroll with arrows to reach hidden tabs; Primer's link nav adds scroll buttons on coarse pointers). *Good:* the header strip's `mask-image` fade at the right edge. *Bad:* `CvSubNav` on a 320 px screen with "Verify" current and off-screen to the right. *Source:* https://www.nngroup.com/articles/tabs-used-right/; Carbon tabs usage, https://carbondesignsystem.com/components/tabs/usage/; Primer UnderlineNav, https://primer.style/product/components/underline-nav/. *Enforced:* smoke screenshots at 390 px. *Q:* "At 320 px, open the last item in each strip: is it visible on arrival?" *Severity:* P2.

## 12. Tabs, segmented controls and accordions

**UX-56. Tabs switch panels inside one page; anything that changes the URL path is a link.** Decide by what happens on click. Same page, different panel: tabs (UX-59). New route: navigation links in a `nav` (UX-49), whatever they look like. Never mix the two in one row. *Why:* NN/g distinguishes in-page tabs from navigation tabs and says not to mix them or make a link look like a tab in a tab control; GOV.UK: do not use tabs "as a form of page navigation"; Carbon: tabs for different content, a content switcher for views of the same content. *Good:* `CvSubNav` (routes) as links with `aria-current`. *Bad:* a row where "Record" and "Statistics" change route but "Motions" swaps a panel on the same URL. *Source:* https://www.nngroup.com/articles/tabs-used-right/; GOV.UK tabs, https://design-system.service.gov.uk/components/tabs/; https://carbondesignsystem.com/components/tabs/usage/. *Q:* "Does clicking each item change the path? Are they all the same kind of control?" *Severity:* P1 if the row mixes the two; P2 otherwise.

**UX-57. Use tabs only for parallel content nobody needs to compare.** If users compare across the sections, read them in order, or most will need only the first, use one page with headings and a jump nav (`PageJumpNav`) instead. *Why:* NN/g: "avoid tabs when users need to compare information across tabs", and non-default tabs hold supplemental content; GOV.UK: tabs hide content and "not everyone will notice them"; test the content without tabs first. For a statistics page, comparison is the point. *Good:* `/cv/stats` as one long page of sections with a jump nav. *Bad:* splitting speaker and team statistics into tabs when the findings refer to both. *Source:* https://www.nngroup.com/articles/tabs-used-right/; https://design-system.service.gov.uk/components/tabs/. *Q:* "Would a user ever want two of these panels on screen at once?" *Severity:* P2.

**UX-58. A segmented control switches views of the same data.** Use it for a filter or a format over one dataset ("Speaking · Judging", "Only me · Everyone", "Table · Chart"), with exactly one option selected. Semantically it is a radio group (`fieldset` + `legend`) or a set of `aria-pressed` buttons (UX-12); if it changes the route, it is navigation (UX-49), even when it looks like a segmented control. *Why:* Carbon's content switcher is for "alternate views of similar or related content", "there should always be one selected", and distinct content areas use tabs instead; Apple asks for no more than about five segments on iPhone. DESIGN_INSTRUCTIONS §5 calls `CvSubNav` a "segmented control"; that describes its look only, and its semantics stay navigation. *Good:* a "Speaking · Judging" pair as `<button aria-pressed>`. *Bad:* the same pair as `div`s with `onClick`. *Source:* Carbon content switcher, https://carbondesignsystem.com/components/content-switcher/usage/; Apple HIG segmented controls (search result), https://developer.apple.com/design/human-interface-guidelines/segmented-controls. *Q:* "Does this control filter one dataset or open a different page?" *Severity:* P2; P1 if it is not keyboard operable.

**UX-59. Real tabs follow the APG keyboard model.** `role="tablist"` with a name; each `role="tab"` has `aria-selected` and `aria-controls`; each `role="tabpanel"` has `aria-labelledby` and `tabIndex={0}` if it has no focusable content first. Only the selected tab is in the Tab order; Left and Right move between tabs and wrap; Home and End are supported. Activate on focus only when the panel is already rendered; if it must fetch, activate on Enter or Space. *Why:* APG tabs pattern; APG recommends automatic activation "as long as their associated tab panels are displayed without noticeable latency"; Carbon: manual activation suits slow content. *Good:* a panel set whose panels are all server-rendered and hidden, switched on focus. *Bad:* each tab a separate tab stop, or a tab that fetches on every arrow press. *Source:* W3C APG tabs, https://www.w3.org/WAI/ARIA/apg/patterns/tabs/; https://carbondesignsystem.com/components/tabs/usage/. *Q:* "Tab into the tabs, press Right three times, press Tab: where is focus?" *Severity:* P1 (keyboard failure, SC 2.1.1 / 4.1.2).

**UX-60. The selected tab or view is in the URL.** Use a readable query value (`?view=judging`, not `?tab=2`), read it on load, replace the history entry when the user switches (so Back leaves the page rather than stepping through tabs), and fall back to the default on an unknown value. Server components read it from `searchParams`, so the right panel renders first time with no flash. *Why:* a shared or reloaded link must open what the user saw (UX-79); readable keys survive reordering. Implementations in GitLab UI and SAP UI5 use the same query-parameter approach with a fallback to the first view. *Good (proposed):* `/cv?view=judging` opening the judging record directly. *Bad:* tab state in `useState` only, so reload returns to the first tab and the link a user sends a friend shows the wrong thing. *Source:* GitLab merge request, "Add tab query param for deep linking" (search result), https://gitlab.com/gitlab-org/gitlab/-/merge_requests/247361; SAP UI5, "Allow Bookmarkable Tabs with Optional Query Parameters" (search result), https://sdk.openui5.org/1.38.62/docs/guide/b8561ff6f4c34c85a91ed06d20814cd3.html; Next.js `Link` `replace`, https://nextjs.org/docs/app/api-reference/components/link. *Enforced:* a unit test of the value parser where one exists. *Q:* "Pick the second view, reload, then press Back: what happens each time?" *Severity:* P2.

**UX-61. Tabs sit directly above their panel, in one row, most used first and selected by default.** No full-width rule or gap between the tab row and its panel; no tabs at the bottom or the side of a data page. *Why:* NN/g: place the tab list above the panel (vertical and bottom placements get overlooked), keep one row, "put high-use content first and select it by default"; GOV.UK: the first tab is the one most users need; Carbon: one tab is always selected, usually the first. *Good (proposed):* "Speaking" first on `/cv`, because more users speak than judge. *Bad:* a default tab chosen by alphabetical order. *Source:* https://www.nngroup.com/articles/tabs-used-right/; https://design-system.service.gov.uk/components/tabs/; https://carbondesignsystem.com/components/tabs/usage/. *Q:* "Which tab do most users need, and is it first and open?" *Severity:* P3; P2 if the default hides the main content.

**UX-62. Tab labels are one or two words; no tab is disabled or hidden by state.** If a tab has no content for this user, either remove it for everyone in that state or keep it and say inside why it is empty (UX-24). *Why:* NN/g and Carbon: one or two words; GOV.UK: "Don't disable tabs" and remove or explain empty ones; Apple: "Don't disable or hide tab bar buttons, even when their content is unavailable". *Good (proposed):* a "Judging" tab that, for a user who never judged, says "No judging rounds found in your tournaments" with a link to Imports. *Bad:* a greyed "Judging" tab that cannot be focused. *Source:* https://www.nngroup.com/articles/tabs-used-right/; https://design-system.service.gov.uk/components/tabs/; Apple HIG tab bars (search result), https://developer.apple.com/design/human-interface-guidelines/tab-bars. *Q:* "Is any tab greyed out? What does it say if opened?" *Severity:* P2.

**UX-63. On a phone, more than three tabs or segments scroll with a visible cue or become a `<select>`; they never wrap.** Prefer an accordion on a phone when the panels are long and independent; keep tabs on desktop. *Why:* NN/g and Carbon: one row only ("should not wrap to multiple lines"); GOV.UK: too many or long labels wrap and break the tab-to-panel link; NN/g accordions: stronger case on mobile, weaker on desktop where collapsed sections make a page look empty. *Good:* a three-segment control that fits 320 px. *Bad:* five segments wrapping to two rows at 360 px. *Source:* https://www.nngroup.com/articles/tabs-used-right/; https://carbondesignsystem.com/components/tabs/usage/; NN/g, "Accordions on Desktop" (2023), https://www.nngroup.com/articles/accordions-on-desktop/. *Enforced:* smoke screenshots at 390 px. *Q:* "At 320 px, is the row one line, and is the selected item visible?" *Severity:* P2.

## 13. Buttons and actions

**UX-64. Links go somewhere; buttons do something.** A control that changes the URL is an `<a>` (`next/link`), even if it is styled as a button with `buttonClasses()`. A control that submits, toggles, opens a dialog or runs an action is a `<button type="button">` (or `type="submit"` in a form), even if it is styled as a link. Never wrap one in the other (UX-9). *Why:* Carbon: "Do not use buttons as navigational elements"; GOV.UK start buttons are links because they do not submit data; links and buttons differ for keyboard (Space does not follow a link), for "open in new tab", and in how screen readers list them. *Good:* "Open imports" as `<Link className={buttonClasses({ variant: 'secondary' })}>`. *Bad:* `<Button onClick={() => router.push('/dashboard')}>`; `<Link><Button>…</Button></Link>`. *Source:* Carbon button usage, https://carbondesignsystem.com/components/button/usage/; GOV.UK button, https://design-system.service.gov.uk/components/button/. *Enforced:* smoke `nested`. *Q:* "Does this control change the URL? Then can I middle-click it?" *Severity:* P1 when nested or when navigation is a `button` (no new-tab, wrong role); P2 otherwise.

**UX-65. At most one primary button per view.** The filled emerald button is the one next step on the screen. Everything else is secondary, ghost or link-styled. A dialog or side panel may have its own primary. *Why:* Carbon: "Primary buttons should only appear once per screen (not including the application header, modal dialog, or side panel)"; Primer: rarely more than one per page; GOV.UK: "Avoid using multiple default buttons on a single page"; Ledger rule 4 (one saturated block per screen). *Good (proposed):* Imports with "Scan Gmail" as the one primary and "Ingest all" secondary. *Bad:* "Scan Gmail", "Ingest all" and "Retry failed" all filled emerald. *Source:* https://carbondesignsystem.com/components/button/usage/; Primer button, https://primer.style/product/components/button/; https://design-system.service.gov.uk/components/button/. *Q:* "Count the filled buttons on screen: is it one?" *Severity:* P2.

**UX-66. Button labels are a verb plus an object.** "Scan Gmail", "Delete account", "Copy link". Allowed single words: Cancel, Close, Done, Save. A dialog's primary label echoes its title ("Delete account?" → "Delete account"). Never "OK", "Yes", "Submit", "Confirm" alone. *Why:* Carbon: "use the {verb} + {noun} content formula on buttons"; Atlassian: the primary button matches the dialog title; NN/g confirmation dialogs: labels that describe the outcome ("Delete file" / "Keep file") instead of Yes/No; NN/g OK–Cancel: explicit labels act as just-in-time help. *Good:* "Disconnect Gmail" / "Keep connected". *Bad:* "Are you sure?" with "Yes" / "No". *Source:* https://carbondesignsystem.com/components/button/usage/; Atlassian modal dialog, https://atlassian.design/components/modal-dialog/usage; NN/g, "Confirmation Dialogs Can Prevent User Errors" (2018, reviewed 2026), https://www.nngroup.com/articles/confirmation-dialog/; NN/g, "OK-Cancel or Cancel-OK?" (2008), https://www.nngroup.com/articles/ok-cancel-or-cancel-ok/. *Q:* "Read only the buttons: do you know what each will do?" *Severity:* P2; P1 on a destructive dialog.

**UX-67. Button order: in-page forms put the primary first; dialogs put it last.** In a form on the page, the primary sits under the last field, left-aligned, followed by any secondary action. In a dialog footer or a sticky action bar, buttons are right-aligned with the primary trailing (rightmost) and Cancel before it. Below `sm`, dialog buttons stack full width with the primary on top. Whatever the context, use one order everywhere. *Why:* sources split by context (see "Where the sources disagree"): GOV.UK and Carbon place the primary on the left for in-page forms; Carbon, Atlassian ("Align buttons on the right in the footer"), Apple alerts (likely choice on the trailing side) and Material Components (confirming action last; stacked, confirming first) place it trailing in dialogs. NN/g: following one convention matters more than which. *Good (proposed):* settings forms with "Save" at the left under the fields; the disconnect dialog with "Cancel" then "Disconnect Gmail" on the right. *Bad:* one dialog with Cancel on the right and the next with it on the left. *Source:* https://design-system.service.gov.uk/components/button/; https://carbondesignsystem.com/components/button/usage/; https://atlassian.design/components/modal-dialog/usage; Apple HIG alerts (search result), https://developer.apple.com/design/human-interface-guidelines/alerts; Material Components dialog (search result), https://classic.yarnpkg.com/en/package/@material/mwc-dialog; https://www.nngroup.com/articles/ok-cancel-or-cancel-ok/. *Q:* "Open every dialog in the app: is the primary in the same place in each?" *Severity:* P2 for inconsistency; P3 for a single off-pattern form.

**UX-68. Page-level actions sit in the page header.** On desktop, actions that apply to the whole page (Export, Share, Scan) sit right-aligned on the `h1` row; on phones they go below the `h1`, before the content, wrapping rather than overflowing (UX-39). Show at most three; put the rest in a "More actions" disclosure (UX-5). *Why:* Atlassian page header: "the action buttons are right-aligned next to the title", one page header per page; Carbon: groups beyond three actions become a menu; NN/g's F-pattern reading puts the page's purpose and actions in the first scan. *Good (proposed):* `/cv` with `h1` "Record" and "Export" and "Share" on the same row at 1280 px, below it at 390 px. *Bad:* the page's export action at the bottom of a long table. *Source:* Atlassian page header, https://atlassian.design/components/page-header/usage; https://carbondesignsystem.com/components/button/usage/. *Q:* "At 390 px, are the page actions visible without scrolling past the data?" *Severity:* P2.

**UX-69. Destructive actions are marked in more than colour and never the default.** The danger style marks the final confirming button only, not the button that opens the confirmation. The label says what is destroyed; focus starts on the safe choice (UX-17). Confirm only what is serious or irreversible; for something undoable, do it and offer Undo. For the rarest, most severe actions (delete account), require typing the account email or slug. *Why:* GOV.UK warning buttons: only for serious, hard-to-undo actions, behind a confirmation step, "don't rely on red alone"; NN/g: overused confirmations train users to click "Yes"; reserve typed confirmation "for the most dangerous and rare actions"; prefer undo. Primer: danger buttons typically prompt a confirmation. Carbon: no icon-only danger buttons. *Good (proposed):* "Remove tag" applied at once with "Undo" in a notice that stays until dismissed (UX-20). *Bad:* a confirmation dialog on "Hide this row", which is reversible. *Source:* https://design-system.service.gov.uk/components/button/; https://www.nngroup.com/articles/confirmation-dialog/; https://primer.style/product/components/button/. *Q:* "Can this be undone? If not, what must the user type or read before it happens?" *Severity:* P1 if an irreversible action has no confirmation; P2 for over-confirmation.

**UX-70. A pending action keeps its label, shows progress, and cannot fire twice.** While a request is in flight the button keeps its text, adds a spinner, sets `aria-disabled="true"` (not `disabled`, which drops focus), ignores further clicks, and the server is idempotent for that action anyway. If it takes over a second, say what is happening nearby (UX-22 beyond ten seconds). *Why:* Primer's `loading` prop shows a spinner, "sets aria-disabled and preserves focus"; GOV.UK prevent-double-click, with server-side protection still needed; Carbon: inline loading on the button. *Good:* `<Button loading>` on "Scan Gmail". *Bad:* a button that changes its label to "…" (the name changes under a screen reader) or sets `disabled`, so focus falls to `<body>`. *Source:* https://primer.style/product/components/button/; https://design-system.service.gov.uk/components/button/; https://carbondesignsystem.com/components/button/usage/. *Enforced:* a test of the `Button` `loading` state where it exists. *Q:* "Click twice fast on a slow network: how many requests go out, and where is focus?" *Severity:* P1 if a double submit can duplicate or destroy data; P2 otherwise.

**UX-71. Avoid disabled controls; if unavailable, stay focusable and say why.** Extends UX-16 to every control. Prefer leaving the control enabled and explaining on use. When it truly cannot work (a cooldown, UX-21), use `aria-disabled="true"`, keep 4.5:1 text contrast, and put the reason in text next to it. *Why:* GOV.UK: "Only use disabled buttons if research shows it makes the user interface easier to understand"; Primer: "Avoid disabling buttons because it will make them inaccessible to users who rely on keyboard navigation", and its inactive state keeps accessible contrast. *Good:* "Scan Gmail" `aria-disabled` with "You can scan again in 1:42" beside it. *Bad:* a greyed button with the reason only in `title`. *Source:* https://design-system.service.gov.uk/components/button/; https://primer.style/product/components/button/. *Q:* "If this is unavailable, where does it say why, and can a keyboard user reach that text?" *Severity:* P2.

**UX-72. Icon-only buttons only for universal icons, always named, with a tooltip.** Allowed: close (×), search, theme, notifications, kebab or chevron for a disclosure. Everything else gets a visible label (wrap rather than truncate). Every icon-only button has an `aria-label` naming the action and, where it repeats, the row (UX-11), and a tooltip on hover and keyboard focus that shows the same words. Hit area at least 24 px, 44 px on touch (UX-8). *Why:* NN/g: few icons are universally recognised, "a text label must be present alongside an icon", and hover-only labels fail on touch; Carbon: "a tooltip is always required" for icon buttons. *Good:* the row report button: flag icon, `aria-label="Report a problem with Worlds 2025"`, tooltip "Report a problem". *Bad:* a download icon with no label for "Export CSV". *Source:* https://www.nngroup.com/articles/icon-usability/; https://carbondesignsystem.com/components/button/usage/. *Enforced:* axe `button-name`. *Q:* "Would a first-time user know what this icon does without hovering?" *Severity:* P1 if unnamed (SC 4.1.2); P2 for an ambiguous icon.

**UX-73. Row actions: one or two visible, named for their row, never hover-only.** A table row shows at most two actions as visible text buttons in the last column; more go into a per-row "Actions for {row}" disclosure. Actions are never revealed only on hover. Bulk actions sit above the table and appear once a row is selected. *Why:* NN/g data tables: inline row actions work only with one or two; hover-revealed actions are hard to discover and low in accessibility; bulk actions above or below the table. SC 1.4.13 and UX-36 (nothing only on hover). *Good (proposed):* Imports' per-row "Ingest" and "Clear" as `size="sm"` buttons (32 px, 44 px coarse) named "Ingest Worlds 2025" (today they are 18 px link-style buttons, UX-8). *Bad:* the `/cv` external-link icon at `opacity-0` until hover. *Source:* NN/g, "Data Tables: Four Major User Tasks" (2022), https://www.nngroup.com/articles/data-tables/. *Q:* "On a touch screen, can every row action be found without long-pressing?" *Severity:* P1 if hover-only; P2 for crowding.

**UX-74. Sticky action bars never hide what has focus.** If a bar is pinned to the bottom (a phone save bar) or the header is sticky, set `scroll-padding` to its height so focused fields and anchor targets are never fully covered, pad for `env(safe-area-inset-bottom)`, and keep one primary in it. Do not pin bars on read-only pages; the phone header already scrolls away by design. *Why:* SC 2.4.11 (AA) fails when a focused component is "entirely hidden due to author-created content"; failure F110 names sticky headers and footers; Next.js skips sticky elements when scrolling and recommends `scroll-padding-top` for a sticky header. *Good (proposed):* `html { scroll-padding-top: 4rem }` under `md:`, matching the desktop sticky header; `globals.css` has no `scroll-padding` today. *Bad:* a fixed bottom bar that covers the last field while it is focused. *Source:* WCAG 2.2 Understanding 2.4.11, https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html; https://nextjs.org/docs/app/api-reference/components/link. *Q:* "Tab through the page at 1280 and at 390 px: is focus ever behind the header or a bar?" *Severity:* P1 if focus is fully hidden (AA failure).

**UX-75. A button group holds at most three buttons of one size.** More than three related actions become one primary or secondary plus a "More" disclosure. Buttons in a group share a size and do not mix two high-emphasis styles. *Why:* Carbon: groups are for two or three actions, "avoid two high-emphasis buttons in one group", keep buttons the same size. *Good (proposed):* "Export" with a "More" disclosure holding CSV, XLSX and JSON. *Bad:* `/admin/tags`' four `nowrap` buttons in one row (also UX-39). *Source:* https://carbondesignsystem.com/components/button/usage/. *Q:* "How many buttons sit side by side here?" *Severity:* P3; P2 if the row overflows at 320 px.

## 14. Wayfinding and page-level navigation

**UX-76. The `<title>`, the `h1` and the active nav label use the same words.** Most specific first: "Sharing · Settings · debate cv" for `/settings/sharing`, "Statistics · debate cv" for `/cv/stats`. Front-load the distinguishing word. *Why:* SC 2.4.2 (title) and 2.4.6 (headings); the Next.js route announcer reads `document.title` first, then the `h1`, so the title is what a screen-reader user hears on every client-side navigation; NN/g F-pattern: users see the first two words. Extends UX-2 and UX-3. *Good:* nav "Imports", `h1` "Imports", title "Imports · debate cv". *Bad:* nav "Imports", `h1` "Dashboard", title "debate cv". *Source:* Next.js accessibility, https://nextjs.org/docs/architecture/accessibility; NN/g, "F-Shaped Pattern" (2017, reviewed 2026), https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/. *Enforced:* smoke `title`. *Q:* "Does the title start with the same word as the `h1`?" *Severity:* P2; P1 if titles are identical across sibling routes.

**UX-77. After a client-side route change, focus starts at the top of the new page.** Next.js announces the new route but does not move focus. Focus must not stay on a link that no longer exists or on the old page's content. Rely on the announcer plus the browser's focus reset for full navigations; for in-app navigations that keep a shared layout, move focus to the new page's `h1` (`tabIndex={-1}`) or to `<main>`. Do not move focus on `?view=` changes inside a page (UX-60); the control the user pressed keeps it. *Why:* SC 2.4.3 (focus order); Next.js: the route announcer reads the title, then the `h1`, then the path, and says nothing about focus; Gatsby's 2019 user testing with disabled users (Fable) led to moving focus and announcing the page on route change. *Good (proposed):* a shared `FocusOnNavigate` client component in the `(app)` layout that focuses the `h1` when `usePathname()` changes. *Bad:* pressing "Settings" and finding the next Tab press lands in the middle of the old page's footer. *Source:* https://nextjs.org/docs/architecture/accessibility; Gatsby, "What we learned from user testing of accessible client-side routing techniques" (2019, search result), https://www.gatsbyjs.com/blog/2019-07-11-user-testing-accessible-client-routing; Gatsby 2.19.8 notes (2020, search result), https://v2.gatsbyjs.com/blog/2020-02-10-accessible-client-side-routing-improvements. *Q:* "Navigate with the keyboard, then press Tab once: is focus at the top of the new page?" *Severity:* P1 on core paths (onboarding, Imports, Record).

**UX-78. New pages start at the top; Back restores position; anchors clear the sticky header.** Leave `next/link`'s default `scroll` behaviour on for page changes; use `scroll={false}` only for in-page view or filter changes (UX-60, UX-80) so the table does not jump. Back and Forward return to where the user was, including in long tables. Set `scroll-padding-top` to the sticky header's height so `#section` links (the stats jump nav) are not hidden. *Why:* Next.js `Link`: scroll defaults to `true`, scrolls to the new page when it is not in view, and skips sticky elements, hence `scroll-padding-top`; NN/g infinite scrolling: losing the place on Back forces users to scroll past what they have seen. *Good:* changing the Imports filter with `scroll={false}`. *Bad:* `/cv/stats#judging` landing with the section heading under the header. *Source:* https://nextjs.org/docs/app/api-reference/components/link; NN/g, "Infinite Scrolling" (2022), https://www.nngroup.com/articles/infinite-scrolling-tips/. *Q:* "Scroll halfway down a table, open a row's page, press Back: where are you?" *Severity:* P2.

**UX-79. Every view worth sharing or returning to has its own URL.** Filters, sort order, the selected view or tab, and the open section are in the URL (path or query), not only in component state. Opening the URL in a new tab, signed in, shows the same view. *Why:* deep links and bookmarks only work if the state is addressable; GOV.UK back links must return users "in the state they last saw it"; NN/g's Back-button guidance. *Good:* `/dashboard?filter=…`: the Imports filter is read from `searchParams`, so a filtered view can be bookmarked. *Bad:* a sort order held in `useState`, lost on reload. *Source:* https://design-system.service.gov.uk/components/back-link/; https://www.nngroup.com/articles/infinite-scrolling-tips/. *Q:* "Set up this view, copy the URL into a new tab: is it the same?" *Severity:* P2.

**UX-80. Filters sit above the table in one row, show when active, and clear in one action.** Show the result count ("12 of 48 tournaments"), mark active filters (chips or a filled control with `aria-pressed` / `aria-current`), and offer "Clear filters" whenever any is on. More than about six filter types move into a "Filters" disclosure, not a sidebar. Distinguish "nothing matches" from "nothing yet" (UX-24). *Why:* NN/g data tables: filters must be discoverable and show "a clear visual indication that filters are active"; its examples put them above the table. Baymard's 2024 ecommerce guidance moved toward sidebars because horizontal toolbars hide options and strain past six to eight filter types. This app has few filter types, wide tables and a phone audience, so the toolbar wins (see "Where the sources disagree"). *Good:* Imports' status chips above the table, with counts. *Bad:* a filter state visible only by the URL changing. *Source:* https://www.nngroup.com/articles/data-tables/; Baymard, "Horizontal filtering and sorting design" (search result; updated March 2025), https://baymard.com/research-articles/horizontal-filtering-sorting-design; Baymard, product-finding 2024 launch (search result), https://baymard.com/research-articles/product-finding-2024-launch. *Q:* "With a filter on, how does the user know, and how do they get back to everything?" *Severity:* P2.

**UX-81. Long lists paginate or "Show more"; nothing infinite-scrolls.** A list over about 50 rows paginates (server-side) or adds a "Show more" button that keeps the earlier rows and the footer reachable. Pagination marks the current page with `aria-current="page"`, has Previous and Next, and on phones shows only first, last, current and its neighbours. Do not paginate a table the user needs to see whole (a season record): use a scroll region instead (UX-29). *Why:* NN/g: infinite scroll does not suit goal-oriented finding or comparing, blocks the footer, and loses position on Back; GOV.UK pagination: avoid infinite scroll, which "causes problems for keyboard users", and the mobile page-number pattern. *Good (proposed):* an admin job list with "Show 50 more". *Bad:* a feed that loads more rows on scroll, so the footer's privacy link can never be reached. *Source:* https://www.nngroup.com/articles/infinite-scrolling-tips/; GOV.UK pagination, https://design-system.service.gov.uk/components/pagination/. *Q:* "Can a keyboard user reach the footer of this page?" *Severity:* P2.

**UX-82. If search is added, it is a visible field that states its scope.** A text input with a visible label (or a visible "Search" button) and a placeholder like "Search tournaments", at the top of the content it searches; not a magnifying-glass icon that opens a field, on desktop. *Why:* NN/g: complex pages "should use a search box", top of the page, wide enough for a typical query; replacing a link with a box nearly doubled use; GOV.UK service navigation: placeholder states the scope ("Search [your service]"). *Good (proposed):* a "Search motions" field above the motions table. *Bad:* a header search icon whose scope is unclear. *Source:* NN/g, "Search: Visible and Simple" (2001), https://www.nngroup.com/articles/search-visible-and-simple/; GOV.UK, navigate a service, https://design-system.service.gov.uk/patterns/navigate-a-service/. *Q:* "What does this search look through, and can you tell before typing?" *Severity:* P3.

**UX-83. Multi-step flows show the steps, the current one and a way back.** The onboarding flow lists its steps with task names ("Connect Gmail", "Find yourself", "Review tournaments"), marks the current with `aria-current="step"` and a visible cue, offers Back on every step after the first, and lets a returning user resume. Do not use a step list where the order is free; use a task list with statuses ("Completed", "Incomplete") instead. *Why:* NN/g wizards: show the steps and highlight the current one, include Next and Previous, name steps for what the user will do; GOV.UK task list: only when users choose the order or cannot finish in one sitting; UX-7 for focus on step change. *Good:* `OnboardingSteps` with `aria-current="step"` and a word for "completed". *Bad:* a step with no Back, so a user who ticked the wrong name must restart. *Source:* NN/g, "Wizards" (2017), https://www.nngroup.com/articles/wizards/; GOV.UK task list, https://design-system.service.gov.uk/components/task-list/. *Q:* "On step 3, can the user see what is left and go back one step without losing work?" *Severity:* P1 if a step is a dead end; P2 otherwise.

**UX-84. Every error, empty and not-found screen offers a real way forward.** A 404, an error boundary or an empty state links to the most likely next page (for a signed-in user, Record or Imports; for a visitor, the landing page), not only "Go home". A public CV that is not shared says so and links to the product, without saying whether the slug exists. *Why:* NN/g heuristic 9 (help users recover) and error-message guidelines (a next step); extends UX-24 and UX-26. *Good (proposed):* `not-found.tsx` offering "Open your record" to a signed-in user. *Bad:* "Something went wrong" with no link. *Source:* https://www.nngroup.com/articles/ten-usability-heuristics/; NN/g error messages, https://www.nngroup.com/articles/error-message-guidelines/. *Q:* "From this screen, how many clicks to a useful page?" *Severity:* P1 if a core path dead-ends; P2 otherwise.

**UX-85. Link text names its destination.** "View Worlds 2025 on the tab", not "here" or "more". Two links with the same text go to the same place; two links to different places do not share text (in a list, add the row, UX-11). *Why:* SC 2.4.4 (A): purpose from the link text and its context; WCAG: "links with different purposes and destinations" should have different text, and SC 3.2.4 asks the same words for the same function; NN/g: front-loaded, specific link text. *Good:* "Open imports". *Bad:* a column of "View" links. *Source:* WCAG 2.2 Understanding 2.4.4, https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html; https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/. *Enforced:* axe `link-name` (empty names only); *Q:* "List the page's links out of context: is each one clear?" *Severity:* P2; P1 if a link has no usable name.

**UX-86. External links open in the same tab unless the user is comparing.** Default to same-tab. Open a new tab only where the user will come back to compare or combine (the tournament's tab pages from `/cv`, where they check a figure against the record). Any new-tab link follows UX-43. External links in the product's own navigation are grouped after internal links. *Why:* NN/g: "always open links in the same browser tab" unless users compare, combine or keep track; avoid new tabs on mobile, where the previous screen is hard to reach; warn before the click. GOV.UK: group external links after internal ones. *Good:* tournament links from the record in a new tab, marked. *Bad:* the privacy policy's link to Google's policy in a new tab with no warning. *Source:* NN/g, "Opening Links in New Browser Windows and Tabs" (2020), https://www.nngroup.com/articles/open-new-windows-for-pdfs/; https://design-system.service.gov.uk/patterns/navigate-a-service/. *Q:* "Why does this link need a new tab?" *Severity:* P3; P2 if unmarked (UX-43).

**UX-87. Help and contact links sit in the same place on every page that has them.** The footer holds Privacy, Terms and the contact or report-a-problem link, in the same order on every page, signed in or out, and on the public CV. *Why:* SC 3.2.6 Consistent Help (A): help repeated across pages must be in "the same order relative to other page content"; it does not require offering help. *Good:* one `Footer` component used by every shell. *Bad:* a "Contact" link in the landing footer but not the app footer, then reappearing in a different position on `/u/[slug]`. *Source:* WCAG 2.2 Understanding 3.2.6, https://www.w3.org/WAI/WCAG22/Understanding/consistent-help.html. *Q:* "Is the help link in the same place on every shell?" *Severity:* P1 if the order differs (an A failure); otherwise none.

## Where the sources disagree (decisions for sections 11-14)

1. **Bottom tab bar or top navigation on phones.** Apple (tab bars) and Material (navigation bar) treat a bottom bar of up to five destinations as the standard for apps. NN/g asks only that navigation stay visible and has no single placement rule for the web. Hoober's grip study is often quoted for bottom placement, but he warns that his reach diagrams came from an informal sample and are not reliable; his firmer finding is that touch concentrates in the centre and corners are least accurate. **Decision:** keep the visible top strip (UX-44). This is a web page in a mobile browser, it is read and scrolled more than switched, and the layout's own note records that pinning chrome cost a fifth of a 390×844 screen. Revisit if usage data show phone users switch sections often.
2. **Primary button left or right.** GOV.UK and Carbon (in-page forms) put it left; Carbon (dialogs, wizards), Atlassian (dialogs), Apple (alerts, trailing side) and Material Components (confirming last) put it right. NN/g says to follow one convention consistently. **Decision:** split by context (UX-67): left in page forms, which are single-column and read top to bottom; trailing in dialogs and action bars, where the desktop users this app is built for expect it.
3. **Breadcrumb current page.** The APG and NN/g include the current page as the last item (NN/g: not a link); GOV.UK ends with the parent. **Decision:** no breadcrumbs today (two levels; UX-52). If they arrive, follow the APG and NN/g, because `aria-current` on the last item also tells screen-reader users where they are.
4. **Automatic or manual tab activation.** The APG prefers automatic activation when panels show without delay; Carbon offers manual for slow content. **Decision:** automatic only for pre-rendered panels; anything that fetches is a separate route or uses manual activation (UX-59).
5. **Disabled buttons.** GOV.UK and Primer say avoid; Carbon disables a button while it loads; Apple says never disable tab bar items. **Decision:** no `disabled` for validation (UX-16); `aria-disabled` with a visible reason for real unavailability and while loading (UX-70, UX-71), which keeps focus.
6. **Filters above or beside the table.** Baymard's 2024 ecommerce update favours sidebars; NN/g's data-table examples put filters above. **Decision:** above (UX-80). Baymard's case rests on many filter types in product catalogues; this app has two or three per table, and a sidebar would take width that wide ledgers need and would collapse to a drawer on phones anyway.
7. **Apple's default button in destructive alerts.** Two versions of Apple's alerts page seen in search results disagree on whether Cancel is the default. **Decision:** NN/g's rule: never default to the destructive choice; focus starts on Cancel (UX-17, UX-69).
8. **"Segmented control" for `CvSubNav`.** DESIGN_INSTRUCTIONS §5 uses the visual term; Carbon and Apple reserve segmented controls for views of the same content. **Decision:** keep the look, keep link semantics (UX-49, UX-58).
