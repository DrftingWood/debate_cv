# CI plan (2026-10-27)

Q1 phase 1b. What runs where, what blocks a merge and what only reports, how a check moves from one to the other, and how to run each one locally. The rules these checks enforce are in `docs/CODING_STANDARDS.md`; the numbers they start from are in `docs/CODE_STANDARDS_BASELINE-2026-10-27.md` (section "Report-only baseline").

## What runs where

| Where | Trigger | What | Blocks? |
|---|---|---|---|
| `.github/workflows/ci.yml`, job **`verify`** | every pull request; every push to `main` | `npm ci`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run ratchet`, `npx next build` | **Yes** once the owner makes `verify` a required check (below) |
| `.github/workflows/ci.yml`, job **`report (non-blocking)`** | same | knip, jscpd, dependency-cruiser, `prettier --check`, `npm audit`, gitleaks; counts written to the job summary | No: every step has `continue-on-error: true` |
| Vercel | push to any branch | `npm run build` (`prisma generate`, migrate when a DB URL is set, `next build`) and the deploy | Vercel's own status; not changed here |
| `drain-queue.yml`, `prescrape.yml`, `prisma-resolve.yml` | schedule / manual | operations, not checks | unchanged |

Nothing in `ci.yml` reads a repository secret. The build runs with no app environment: every route that touches the database or Auth.js is dynamic, so `next build` needs none (checked locally, 2026-10-27). It calls `next build` directly rather than `npm run build`, so `scripts/migrate-if-configured.mjs` never runs in CI. If a future page needs a value at build time, give it an obviously fake placeholder in the workflow, never a secret.

### Design choices in `ci.yml`

- `permissions: contents: read` at the top: the token can read the repo and nothing else, and every unlisted permission becomes `none` ([workflow syntax, `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)).
- `concurrency: ${{ github.workflow }}-${{ github.head_ref || github.ref }}` with `cancel-in-progress` only for pull requests: a new push to a PR branch cancels the stale run; runs on `main` always finish (same page, `concurrency`).
- `actions/setup-node` with `cache: npm` caches npm's download cache keyed on `package-lock.json`, not `node_modules`; `npm ci` still installs from the lockfile ([setup-node README](https://github.com/actions/setup-node)). The README advises turning caching off for privileged workflows; this one is read-only.
- `.next/cache` is cached with `actions/cache`, keyed as the [Next.js CI caching guide](https://nextjs.org/docs/app/guides/ci-build-caching) suggests, but hashing only `app/`, `lib/`, `components/` and root config (hashing `**/*.ts` would walk `node_modules`).
- Every action is pinned to a full commit SHA with the tag in a comment (checklist L6).
- In `verify`, steps after the first use `if: ${{ !cancelled() }}`, so a PR sees every failing check in one run. The job still fails if any step fails.
- The report job writes one Markdown table to `$GITHUB_STEP_SUMMARY` through `scripts/ci-report-summary.mjs` ([job summaries](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands); 1 MiB per step limit).

### Node version

Both jobs use Node 20 because `package.json` says `"node": ">=20"` and the brief asked for it. **Node 20 is listed as End-of-Life** on [nodejs.org/en/about/previous-releases](https://nodejs.org/en/about/previous-releases) (read 2026-10-27). Moving CI, `engines` and the Vercel project setting to Node 22 or 24 together is an owner decision; when it happens, dependency-cruiser can move from 17.4.3 to 18.x (18 requires Node 22+, which is why 17 is pinned now).

**Lockfile note.** The first `npm install --save-dev` (npm 11.6.2) dropped the optional `@emnapi/core` and `@emnapi/runtime` entries from `package-lock.json`, and `npm ci` then refused the lockfile ("Missing: @emnapi/runtime@1.11.3"). A plain `npm install` afterwards restored them, and local `npm ci` passed, but the first CI run still failed: CI's Node 20 ships npm 10, which wants nested copies of `@emnapi/core` and `@emnapi/runtime` 1.11.2 under `@oxc-resolver/binding-wasm32-wasi` (it pins that exact version) and npm 11 had not written them. The lockfile was then regenerated with `npx npm@10.8.2 install --package-lock-only`; it passes `npm ci` under both npm 10.8.2 and npm 11.6.2. Its only changes to existing packages are patch and minor bumps of transitive dependencies that the new tools share (`semver` 7.8.1, `enhanced-resolve` 5.22.1, `jiti` 2.7.0, `@emnapi/*` and a few more), all published more than two weeks ago. After any dependency change, run `npx -y npm@10 ci` once before pushing (or update the lockfile with npm 10 in the first place), because CI installs that way with npm 10. This goes away when CI moves off Node 20.

`npm audit` is npm's own and needs no install. OSV-Scanner (v2.7.0, 2026-10-12, https://github.com/google/osv-scanner) was considered and left out: it would be a second binary download for overlapping data, and `npm audit` already covers the npm graph. Revisit if a non-npm ecosystem (the Python reference parser) needs scanning.

## Blocking checks (`verify`)

| Step | Command | Fails when |
|---|---|---|
| Install | `npm ci` | `package.json` and `package-lock.json` disagree (DP-1) |
| Typecheck | `npm run typecheck` | any TypeScript error, including the new `noUnusedLocals` / `noUnusedParameters` (TE-2) |
| Lint | `npm run lint` | any ESLint **error**. Warnings (360 today, all size and complexity) do not fail. The one error-level rule added here is `no-restricted-syntax` against `new PrismaClient` outside `lib/db.ts` and `scripts/` (DB-1), at 0 hits |
| Test | `npm test` | any Vitest failure. Live suites skip without their env. **Known flake:** `tests/queueDrain.test.ts` › "overlaps jobs on distinct hosts" asserts a wall-clock time under 120 ms; it failed once locally (139 ms) while a build ran alongside, and passed on re-run. If it fails on a shared runner, it needs fake timers (TQ-3), not a retry |
| Ratchet | `npm run ratchet` | any escape-hatch count above its baseline (ST-6) |
| Build | `npx next build` | the production build fails |

### How each config was tuned

- **knip**: the Next.js and Vitest plugins find the routes and tests on their own; `knip.json` adds the standalone `scripts/*.mjs` and the Sentry config files as entries, and ignores `eslint-config-next`, which `eslint.config.mjs` loads by name through `FlatCompat` where knip cannot see it. Without those, the first run reported the scripts as unused files and four tools as unused devDependencies. Reporters: https://knip.dev/features/reporters ; config: https://knip.dev/reference/configuration
- **jscpd**: thresholds are its defaults (5 lines, 50 tokens), which match the "duplicated 5+ line blocks" measure in checklist §15. `mode: mild`. Tests are excluded. jscpd 5 is a native rewrite; options are in `npx jscpd --help` and https://github.com/kucherenko/jscpd
- **dependency-cruiser**: `tsPreCompilationDeps: true` so that `import type` is visible, which lets the Prisma rule skip type-only imports and still shows type-only cycles. Of the 5 cycles, 2 are value cycles (`lib/db.ts → lib/queueDrain.ts → lib/queue.ts → lib/db.ts`, and the same loop through `lib/notifications/write.ts`); the other 3 each contain one type-only edge and are harmless at runtime. `node_modules` is not excluded (that hid `@prisma/client` from the rule on the first try); `doNotFollow` keeps it out of the walk. Rules: https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md
- **Prettier**: measured first. Over the 374 TypeScript files: imports use single quotes 1,335 to 10; 18,231 lines end in `;`; multi-line lists end with a trailing comma 2,273 to 111; 2-space indent, no tabs; `(x) =>` 1,205 to 2. For width, the number of lines Prettier would change was 5,682 at 80, 4,130 at 90, **3,694 at 100**, 3,891 at 110 and 4,125 at 120, so `printWidth: 100`. `endOfLine: "auto"` because a Windows checkout has CRLF in the working tree while git stores LF; `"lf"` would flag every file locally ([options](https://prettier.io/docs/options)). `.prettierignore` keeps out the lockfile, migrations, `docs/` (prose) and test fixtures (the parser tests read their exact bytes). The repo was **not** reformatted; only the new files in this PR were.
- **npm audit**: reports all dependencies, dev included, at `--audit-level=high` ([npm audit](https://docs.npmjs.com/cli/v11/commands/npm-audit)). The four devDependencies added here add no advisories (the counts are identical on `main`'s lockfile).
- **gitleaks**: scans every commit (`fetch-depth: 0`), redacted output ([gitleaks](https://github.com/gitleaks/gitleaks)). The first run found 3 `generic-api-key` hits; all three are prose or a table row in docs (a sentence about Tabbycat API pages, and the API path `speakers/standings/rounds`). They are listed by fingerprint in `.gitleaksignore` with the reason.

## How a check graduates from warning to error

One rule, the same for lint warnings, dependency-cruiser rules and report-only tools:

1. **Report.** The check runs, the count is in the job summary and in the baseline doc.
2. **Ratchet.** Once someone starts reducing it, each PR that lowers the count also lowers the recorded baseline, as `scripts/check-ratchet.mjs` does today. A PR may not raise it without a reason in its body.
3. **Block.** When the count reaches zero (or zero plus a short, named exemption list), flip it: ESLint `warn` → `error`; dependency-cruiser `severity: 'warn'` → `'error'` (the `err` reporter then exits non-zero); a report-only tool moves from the `report` job to the `verify` job and loses `continue-on-error`. Do it in a PR of its own that changes nothing else, and record the date in the baseline doc.

Candidates, in the order they are likely to reach zero:

| Check | Today | Next step |
|---|---|---|
| dependency-cruiser `lib-not-to-app-or-components` | 0 | can block now; left as report for one cycle so the owner sees it run |
| `no-restricted-syntax` (PrismaClient) | 0 | already blocking |
| knip unused dependencies / unused files | 0 / 0 | can block after a cycle; unused exports (31) need a cleanup PR first |
| gitleaks | 0 | move to `verify` once it has run green on a few PRs; then consider GitHub push protection instead |
| dependency-cruiser `no-circular` | 5 (2 value) | break the `db.ts` ↔ `queueDrain.ts` loop by moving `DRAIN_CONCURRENCY`; decide whether type-only cycles count |
| npm audit high+ | 21 | an upgrade PR (Next, next-auth, Sentry, Vitest are the critical ones); then block on new criticals only |
| jscpd | 2.73% | set `threshold` at the current figure so it cannot rise, then lower |
| Prettier | 294 files | only after the owner decides whether to reformat the repo in one commit (with a `.git-blame-ignore-revs` entry) or file by file |
| size and complexity lint | 360 warnings | Q1 phase 3 splits; promote each rule at zero |

`noUnusedLocals` and `noUnusedParameters` skipped the ladder: they produced **0 errors** when enabled (`tsc --noEmit --incremental false`), so they went straight into `tsconfig.json` and are blocking through `typecheck`.

## Running each check locally

```bash
npm ci                     # once
npm run typecheck          # blocking in CI
npm run lint               # blocking (errors only)
npm test                   # blocking
npm run ratchet            # blocking; add -- --verbose to list every hit
npx next build             # blocking; no env needed

npm run knip               # report; exits 1 when it finds anything
npm run dup                # report; writes .reports/jscpd/
npm run arch               # report; prints violations, exits 0 while rules are 'warn'
npm run format:check       # report; exits 1 when any file differs
npm audit --audit-level=high
gitleaks git . --redact    # needs the gitleaks binary (8.30.1)
```

To reproduce the job summary table, write the raw outputs to `.reports/` (git-ignored) as the `report` job does, then `node scripts/ci-report-summary.mjs`:

```bash
mkdir -p .reports
npx knip --no-exit-code --reporter json > .reports/knip.json
npm run dup
npx depcruise app lib components middleware.ts instrumentation.ts -T json -f .reports/depcruise.json
npx prettier --list-different "**/*.{ts,tsx,js,mjs,cjs,json,css}" > .reports/prettier.txt
npm audit --json > .reports/audit.json
gitleaks git . --redact --report-format json --report-path .reports/gitleaks.json
node scripts/ci-report-summary.mjs
```

To validate a workflow change: `actionlint .github/workflows/ci.yml` (https://github.com/rhysd/actionlint).

## One-time GitHub settings for the owner

This PR does not touch branch protection or repository settings. After it merges and `CI` has run once on `main` (a check name only appears in the picker after it has run):

1. **Settings → Rules → Rulesets → New branch ruleset** (or Settings → Branches → Add classic branch protection rule), target `main`:
   - Require a pull request before merging.
   - Require status checks to pass → add **`verify`**. That is the job's `name:` in `ci.yml`; the picker may show it as `verify` with "GitHub Actions" as the source. Do **not** add `report (non-blocking)`.
   - "Require branches to be up to date before merging": optional. On means every PR re-runs CI after any merge to `main` (stricter, more runs) ([ruleset rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
   - Block force pushes.
2. **Settings → Actions → General → Workflow permissions**: "Read repository contents and packages permissions". `ci.yml` already asks for only `contents: read`; this makes it the default for the older workflows that do not set `permissions` (`prisma-resolve.yml`).
3. **Settings → Code security**: turn on Dependabot alerts, and secret scanning with push protection if the plan offers it. Push protection stops a secret before it lands, which gitleaks can only find after.
4. If the required check never appears, check that Actions is enabled for the repository and that the workflow ran on a PR at least once.
